0056 · Session cookie sealed with a key held in the database, replacing ASP.NET Data Protection

Status: accepted

Context and Problem Statement

ADR-0027 chose Google OpenID Connect with a backend-for-frontend session cookie. The .NET API issues that cookie with ASP.NET cookie authentication: a stateless ticket, encrypted by ASP.NET Data Protection, whose key ring is persisted in the DataProtectionKeys table so sessions survive restarts and are shared by replicas. ADR-0032 left the key ring’s storage as “a related but separate decision”, and no record took it. The backend moves to Rust (ADR-0051), which has neither cookie authentication nor Data Protection. How does the Rust API seal the session cookie, and where does the key live?

The sign-in flow itself is not reopened: Google’s authorization code flow, the verified-email allow-list, same-origin only, 401 for API callers and the Development seed key stay as ADR-0027 decided.

Decision Drivers

  • D1 Browser security: the cookie is HttpOnly, cannot be read or forged without the key, and the key is hard to obtain.
  • D2 No infrastructure change: no new configuration name, Key Vault secret or Bicep change at the cutover (ADR-0051 D4).
  • D3 Restarts and replicas: a session survives a restart or a new revision, and every replica accepts it.
  • D4 Revocation and rotation: a session or a key can be ended before its lifetime runs out.
  • D5 Like-for-like port: the behaviour the C# tests specify (stateless cookie, eight-hour absolute lifetime, no extra query per request) carries over with little new surface.
  • D6 Sessions across the cutover: people signed in before the cutover stay signed in.

Considered Options

  • Stateless sealed cookie with the key in a session_keys table
  • Stateless sealed cookie with the key in Key Vault
  • Server-side sessions in a table, with an opaque identifier in the cookie
  • Read and write ASP.NET Data Protection’s cookie format from Rust

Decision Outcome

Chosen option: “Stateless sealed cookie with the key in a session_keys table”, because it keeps what the .NET API does today, a stateless encrypted cookie whose key is in the application’s database, with the same lifetime and attributes (D5), needs no infrastructure change (D2) and works across restarts and replicas (D3). It ends existing sessions at the cutover (D6) and, like today, cannot revoke a single session (D4). The maintainer chose it on 2026-11-11.

Conventions

  • Cookie: HttpOnly, SameSite=Lax, Secure outside Development, path /. These are the attributes the .NET API sets.
  • Lifetime: eight hours, absolute, no sliding renewal. The expiry instant is inside the sealed payload and is checked against the injected clock (ADR-0054); the cookie’s own expiry attribute is not trusted.
  • Sealing: authenticated encryption (AEAD) from a maintained Rust crate, XChaCha20-Poly1305 from chacha20poly1305, with a fresh random nonce for every cookie and a format version byte. The cookie’s purpose is bound in as associated data, so a sign-in cookie cannot stand in for a session cookie. The API never implements a cipher itself. A cookie that fails to open or has expired is treated as no session: 401 for an API call, as today. The session cookie is named calendar_session.
  • Payload: only what the API needs to identify the user and answer GET /api/auth/me: the user’s id and display fields (name, email, picture) and the expiry instant. No Google token is stored in it.
  • Key: random bytes of the cipher’s key length, generated by the operating system’s random source, stored in a session_keys table that holds at most one row, with its creation time. The API creates the key the first time it needs one (INSERT ... ON CONFLICT DO NOTHING, then read), so replicas that start together agree on it, and each instance keeps the key it loaded until it stops. Rotation is an operator action as calendar_migrator: delete the row, then restart every replica, which ends every session. The key is never logged and never leaves the database and the API’s memory.
  • Schema: the seventh migration creates session_keys and drops DataProtectionKeys (ADR-0052). calendar_app may insert and read the key but not update or delete it.
  • Same key, other short-lived cookies: the sign-in flow’s state cookie (calendar_signin: state, PKCE verifier, nonce and return URL, 15 minutes) is sealed the same way.
  • Cutover: everyone signs in again once. This is announced in the pull request and the release notes, not worked around.

Effect on earlier records

These edits were made when this record was accepted, on 2026-11-11.

  • ADR-0027 stays accepted and gets a dated amendment bullet that points here: its chosen option, the BFF cookie, stands, and its conventions never named the sealing mechanism. This record adds that mechanism; it does not replace the decision.
  • ADR-0032 gets a dated amendment bullet: the “related but separate decision” about the Data Protection key ring is taken here for the Rust backend, and the key is deliberately not a Key Vault secret.

Consequences

  • Good, because sign-in, sign-out, expiry and the 401 behaviour look the same to the browser and the frontend.
  • Good, because no secret, configuration name or Azure resource is added.
  • Bad, because existing sessions end at the cutover: every signed-in person is sent to the sign-in page once.
  • Bad, because anyone who can read session_keys can forge a session for any user until the key is replaced. That includes anyone with the application’s database credentials and any SQL injection in the API. The exposure is the same as today’s: DataProtectionKeys holds its keys unencrypted and calendar_app reads them.
  • Bad, because a single session cannot be revoked. Signing out clears the cookie in that browser; a copied cookie stays valid until its eight hours end. Deleting the key ends every session at once. ASP.NET cookie authentication behaved the same way.
  • Bad, because the sealing code is ours to get right (nonce handling, key lookup, expiry check), where ASP.NET shipped it. The cipher is a library’s; the envelope is not.
  • Bad, because there is no automatic key rotation, which Data Protection did every 90 days by default.
  • Neutral, because a rollback to the .NET image after the seventh migration needs DataProtectionKeys recreated; ASP.NET then generates a new key ring, and sessions end again.

Confirmation

  • API tests port the C# session tests: anonymous 401, allowed and denied accounts, sign-out, the return path, and expiry at eight hours by advancing the injected clock.
  • New tests cover a tampered cookie, a cookie sealed with an unknown key, an expired cookie whose browser expiry was extended, and two application instances that share a database accepting each other’s cookies.
  • A database test checks calendar_app’s rights on session_keys.
  • The image smoke test checks the cookie attributes over the container; the Secure attribute behind the Azure ingress stays a deployment check (ADR-0027).
  • The security-reviewer agent reviews the sealing code in the code pull request.

Pros and Cons of the Options

Stateless sealed cookie with the key in a session_keys table

  • Good, because D2 No infrastructure change: the key arrives through a migration, in the database the API already uses.
  • Good, because D3 Restarts and replicas: every instance reads the same key.
  • Good, because D5 Like-for-like port: the same model as ASP.NET cookie authentication with a persisted key ring, so the existing tests port directly, and no request needs an extra query once the key is cached.
  • Neutral, because D1 Browser security: JavaScript cannot read the cookie and it cannot be forged without the key, but the key sits beside the data it protects, unencrypted.
  • Bad, because D4 Revocation and rotation: no per-session revocation; rotation is a manual insert, and removing a key ends all sessions.
  • Bad, because D6 Sessions across the cutover: the old cookies cannot be opened.

Stateless sealed cookie with the key in Key Vault

  • Good, because D1 Browser security: the key is outside the database, so reading the database is not enough to forge a session, and vault access is audited (ADR-0032).
  • Good, because D3 Restarts and replicas: every instance gets the same secret.
  • Neutral, because D4 Revocation and rotation: vault versions give rotation a place, but accepting the previous key during a rotation is still ours to build; no per-session revocation.
  • Neutral, because D5 Like-for-like port: the same cookie, but local development and tests need another source for the key.
  • Bad, because D2 No infrastructure change: a new secret, a new configuration name and a Bicep change in every environment, which the maintainer ruled out for this cutover.
  • Bad, because D6 Sessions across the cutover: the old cookies cannot be opened.

Server-side sessions in a table, with an opaque identifier in the cookie

  • Good, because D1 Browser security: the cookie holds a random identifier and no data; there is no key to steal, although database write access can still create a session.
  • Good, because D2 No infrastructure change: a table in the existing database.
  • Good, because D3 Restarts and replicas: sessions are rows.
  • Good, because D4 Revocation and rotation: deleting a row ends one session at once; sign-out is real.
  • Bad, because D5 Like-for-like port: a different model from today’s: a query on every request, expired rows to clean up, and new behaviour that no existing test specifies.
  • Bad, because D6 Sessions across the cutover: the old cookies have no rows.

Read and write ASP.NET Data Protection’s cookie format from Rust

  • Good, because D6 Sessions across the cutover: existing cookies keep working, and a rollback to the .NET image needs nothing.
  • Good, because D2 No infrastructure change: DataProtectionKeys stays as it is.
  • Good, because D3 Restarts and replicas: the same shared key ring.
  • Neutral, because D1 Browser security: the same exposure as today, plus the risk of a subtle mistake in a reimplemented format.
  • Bad, because D4 Revocation and rotation: as today for sessions, and the key ring’s rotation and expiry rules would have to be reimplemented too.
  • Bad, because D5 Like-for-like port: the key ring’s XML, the key derivation, the payload framing and the authentication ticket’s binary serialization are ASP.NET internals with no Rust implementation to reuse; the work buys eight hours of continuity, once.
