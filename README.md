# Calendar

[![Documentation](https://img.shields.io/badge/Documentation-blue?style=flat-square&logo=readme)](https://mgasca.github.io/calendar/)

Monorepo for the Calendar application: a .NET backend and a web front end, with room for more UIs.

Create todo tasks from the calendar or **My tasks**, with optional date or exact-time deadlines, priority, and notes. Review Upcoming, Overdue, Completed, and No deadline lists. See the [task story and user guide](docs/stories/0003-add-todo-tasks.md). Apply the new migration with `make db-migrate` before running an existing database.

## Layout

```
backend/                 .NET 10 solution (Calendar.slnx)
  src/Calendar.Domain/     Domain model; no framework dependencies
  src/Calendar.Infrastructure/  EF Core DbContext, mappings, migrations (PostgreSQL)
  src/Calendar.Api/        ASP.NET Core minimal API
  tests/                   xUnit v3 test projects (one per src project) + Calendar.Testing (Testcontainers support)
compose.yaml             Local backing services (PostgreSQL); init scripts in docker/postgres/init/
contracts/openapi.json   API contract, generated by the backend build — commit changes
frontend/                pnpm workspace
  apps/web/                React + Vite + TypeScript web UI
  apps/docs/               Astro + Starlight reader for ADRs and user stories
  packages/api-client/     Typed client generated from contracts/openapi.json, shared by all TS UIs
docs/decisions/          Architecture Decision Records (MADR)
docs/stories/            User stories: background, decisions, implementation notes, user guide
.github/                 CI and Dependabot
```

New UIs go under `frontend/apps/` (TypeScript) or a new top-level directory for other stacks; they should consume `contracts/openapi.json`.

## Prerequisites

| Tool | Version source | Notes |
| --- | --- | --- |
| .NET SDK | `backend/global.json` | 10.0.100 or later feature band |
| Node | `frontend/.node-version` | 24; use a version manager, since Ubuntu's apt `nodejs` is too old and lacks Corepack |
| pnpm | `packageManager` in `frontend/package.json` | Provided by Corepack (bundled with Node 24); don't install it globally |
| Docker | n/a | Engine running and reachable; needed for the local database and for integration tests (Testcontainers) |

Run `make doctor` (also run by `make setup`) to check all of these.

### One-time setup on Linux / WSL

```sh
# .NET SDK, user-local (no sudo)
curl -sSL https://dot.net/v1/dotnet-install.sh -o /tmp/dotnet-install.sh
bash /tmp/dotnet-install.sh --channel 10.0 --install-dir "$HOME/.dotnet"
echo 'export DOTNET_ROOT=$HOME/.dotnet PATH=$HOME/.dotnet:$HOME/.dotnet/tools:$PATH' >> ~/.bashrc

# Node via fnm, which reads .node-version and switches automatically on cd
curl -fsSL https://fnm.vercel.app/install | bash -s -- --skip-shell
echo 'eval "$(fnm env --use-on-cd --version-file-strategy=recursive --corepack-enabled --shell bash)"' >> ~/.bashrc
exec bash                      # reload the shell
cd calendar/frontend && fnm install && corepack enable pnpm

make doctor                    # everything should be ✓
```

## Documentation website

The Astro + Starlight site renders the canonical Markdown in `docs/decisions/` (the ADR log, at `/adr/NNNN/`) and `docs/stories/` (the user stories, at `/stories/NNNN/`). Every ADR and story merged to `main` is published, including proposed and superseded decisions. Links between ADRs and stories, and from stories to the code they reference, work on the published site. Edit the Markdown sources there; generated pages are build output and are not committed.

After installing the frontend dependencies with `pnpm --dir frontend install --frozen-lockfile`, use `make dev-docs` to develop the site. `make build-docs` builds and verifies the static output in `frontend/apps/docs/dist`; `make preview-docs` serves that output. These tasks require Node and pnpm, but do not require the backend or database.

To reproduce the GitHub Pages project path locally:

```sh
DOCS_SITE_URL=https://mgasca.github.io/calendar/ make build-docs
DOCS_SITE_URL=https://mgasca.github.io/calendar/ make preview-docs
# Open http://localhost:4321/calendar/
```

`DOCS_SITE_URL` is the full public URL, including any project path. The site derives its origin and base path from this URL, so custom domains and root-hosted sites work without hard-coded `/calendar/` links. Local development defaults to the site root.

GitHub Pages uses **Settings → Pages → Build and deployment → Source: GitHub Actions**. CI builds and checks the site for pull requests, merge queues, and manual runs. Successful `main` push builds update production; successful same-repository PR builds update their preview. The separate **Publish ADR site** workflow accepts artifacts only from successful CI runs with a current source revision, then publishes through the `github-pages` environment. Keep its deployment branch rule restricted to `main`: the publisher runs trusted default-branch workflow code even when publishing PR artifacts.

The configured publication URL is [mgasca.github.io/calendar](https://mgasca.github.io/calendar/). The site becomes available after the workflow's first successful deployment from `main`; an unmerged branch or pull request does not update it.

### Pull request previews

After CI succeeds, a PR from this repository gets an **ADR preview** check linking to `https://mgasca.github.io/calendar/pr-preview/pr-<number>/`. Each new successful revision replaces that PR's preview; closing or merging the PR removes it. Fork PRs run CI but do not publish previews. Manual CI runs and merge-queue runs do not publish either.

The publisher retains generated production files and preview directories on the `gh-pages` branch. That branch is storage for the combined artifact, **not** the Pages publishing source: leave Pages configured for GitHub Actions. A production update preserves open previews, a preview update preserves production, and queued publication serializes snapshot reads, updates, and deployment. The publisher also removes closed PR directories during subsequent publications. Do not edit the generated branch manually.

The privileged publisher downloads only static artifacts, rejects non-regular and reserved paths, and never checks out or executes PR code. It rechecks the current PR head or `main` revision before updating the snapshot. Previews share the production origin, so they are intended for trusted repository contributors; unreviewed preview JavaScript has the same origin as production documentation. No third-party hosting account or extra deployment secret is needed. See [ADR-0025](docs/decisions/0025-github-pages-pr-previews.md).

**First setup:** merge the preview infrastructure into `main` first. Its successful CI run creates the initial production snapshot. Then rerun CI by pushing a commit to the UI PR branch (or use GitHub's **Re-run all jobs** on its `pull_request` run). GitHub loads `workflow_run` automation from the default branch, so an unmerged infrastructure PR cannot enable its own preview. A preview run arriving before the first production snapshot is skipped with a notice; rerun that PR's CI after production succeeds. The preview URL appears in the PR's **ADR preview** check and publisher run summary. If the publisher fails, inspect **Actions → Publish ADR site** and rerun that workflow; do not dispatch CI manually to publish.

### Local database

```sh
make db-up        # starts PostgreSQL on 127.0.0.1:5432; creates .env from .env.example on first run
make db-migrate   # applies EF Core migrations as calendar_migrator
```

`.env` is untracked and holds disposable local passwords. The database creates two roles: `calendar_migrator` (owns the schema, runs migrations) and `calendar_app` (DML only; the API always connects as this role). Migrations are never applied at API startup.

Give the API its connection string with user-secrets (no secret is ever committed to `appsettings*.json`). Use the `CALENDAR_APP_PASSWORD` from your `.env`:

```sh
dotnet user-secrets set "ConnectionStrings:Calendar" \
  "Host=127.0.0.1;Port=5432;Database=calendar;Username=calendar_app;Password=dev-app-password" \
  --project backend/src/Calendar.Api
```

or set the environment variable `ConnectionStrings__Calendar`. In Development the API logs EF Core SQL commands. Integration tests need no setup beyond a running Docker daemon: they start their own throwaway PostgreSQL (the image pinned in `compose.yaml`) with `Calendar.Testing`.

> **Adding a backing service?** Re-evaluate .NET Aspire for local orchestration before wiring it into Docker Compose by hand, and add a row here. See [ADR-0016](docs/decisions/0016-local-database-provisioning.md).

### Google sign-in setup

Create a Google OAuth web application client and configure its authorized redirect URIs for each environment:

* Development: `http://localhost:5173/api/auth/callback/google`
* Production: `https://<host>/api/auth/callback/google`

Set `Auth__Google__ClientId`, `Auth__Google__ClientSecret` and indexed entries such as `Auth__AllowedEmails__0` in the untracked `.env` for local development, then export them into the API process (`make dev-api` loads `.env` for you; restart it after editing, since hot reload does not re-read the environment); use deployment secrets for production. Add only the verified Google emails permitted to access the calendar. Keep the client secret out of version control. Use HTTPS in production and configure trusted forwarded headers when behind a proxy so redirects and secure cookies use the public origin.

> **Authentication and limitations.** Google sign-in protects the API with a same-origin cookie ([ADR-0027](docs/decisions/0027-google-oidc-bff-session.md)). All allowed accounts currently share the same data: add `owner_id` and per-user scoping before supporting a second user. Add bearer support before enabling non-browser clients.
