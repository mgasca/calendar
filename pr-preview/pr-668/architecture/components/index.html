Components

Every element of the model. Each page lists the interfaces the element exposes, the relationships it takes part in, the controls it must satisfy and the decisions behind it.

ComponentTypeDescriptionDecisions
Calendar useractorA person whose verified Google email is on the allow-list. Uses the web app in a browser to see today and the week, add events and tasks, tick tasks off and triage overdue tasks.ADR-0027
Maintainer / operatoractorThe repository owner who merges pull requests, deploys infrastructure with the infra tool, initialises secrets and roles, runs database migrations and approves production deployments.ADR-0033, ADR-0034, ADR-0035
Google Identity (OpenID Connect)systemExternal identity provider. The API runs the OpenID Connect authorization-code flow against it; the browser is redirected to Google to sign in and back to the API callback with a code.ADR-0027
Calendar systemsystemThe whole product: web app, API, generated client, contract, database, migrator and documentation site, all developed in the single repository mgasca/calendar.ADR-0001, ADR-0002, ADR-0003, ADR-0030
Calendar web appwebclientReact 19 + Vite + TypeScript single-page app (frontend/apps/web). TanStack Router with code-based routes for /, /day/$date, /week, /week/$weekStart, /tasks, /triage and /signin; TanStack Query for server state. Reads the browser’s IANA time zone and local date and sends them with every agenda request. Served as static files from the API container (same origin, no CORS).ADR-0003, ADR-0005, ADR-0008, ADR-0010, ADR-0021, ADR-0026, ADR-0030
@calendar/api-clientlibraryTypeScript package (frontend/packages/api-client) generated from contracts/openapi.json with openapi-typescript; createApiClient wraps openapi-fetch with the typed paths. schema.gen.ts is never hand-edited. Shared by every TypeScript UI so that no UI depends on backend code.ADR-0004, ADR-0005
OpenAPI contractdata-assetcontracts/openapi.json: the committed OpenAPI 3 document emitted by the API build. It is the single contract between the backend and every client; CI fails when it is stale.ADR-0004
Calendar APIserviceASP.NET Core minimal API on .NET 10 (backend/src/Calendar.Api) with a framework-free Calendar.Domain (time-zone and day-inclusion rules) and Calendar.Infrastructure (EF Core 10 on Npgsql, SQL forms of the domain rules). Serves events, tasks, day and week agenda read models and Google sign-in with a cookie session; also serves the SPA’s static files and index.html fallback. Every endpoint requires an authenticated user except health and sign-in.ADR-0002, ADR-0004, ADR-0006, ADR-0007, ADR-0009, ADR-0015, ADR-0018, ADR-0020, ADR-0021, ADR-0024, ADR-0027, ADR-0030, ADR-0036, ADR-0041
Calendar database (PostgreSQL 18)databaseThe ‘calendar’ PostgreSQL database: users (keyed by Google’s subject), events (owned by a user, with generated tstzrange/daterange spans and GiST indexes), tasks (owned by a user, with partial B-tree indexes led by owner_id for due and open-overdue lookups) and the Data Protection key ring. Locally postgres:18.6-alpine in Docker Compose on 127.0.0.1:5432; in Azure a Flexible Server (Burstable Standard_B1ms, 32 GB, TLS required) per environment.ADR-0014, ADR-0015, ADR-0016, ADR-0031, ADR-0035, ADR-0037, ADR-0041
Database migratorserviceThe only path that changes the schema: EF Core migrations applied as calendar_migrator. Locally just db migrate (dotnet ef database update); in Azure just infra migrate <env> builds an idempotent migration bundle and runs it, from the manually dispatched ‘Database migration’ GitHub Actions workflow. A failed bundle leaves the existing revision serving.ADR-0015, ADR-0031, ADR-0034
Infrastructure toolservice.NET 10 file-based app (tools/infra) driven by the just infra module: just infra what-if and just infra deploy <env> [foundation|full] run the Bicep deployment with the Azure CLI, just infra secret-init stores the PostgreSQL admin password in the ops vault, just infra init-roles creates the database roles, just infra db-stop and db-start manage the staging server. Pinned Azure CLI and Bicep versions are verified by just doctor.ADR-0017, ADR-0033, ADR-0034
GitHub Actions (CI/CD)serviceWorkflows in .github/workflows: CI (a Changes job that decides from the changed paths which jobs a pull request or merge group needs; backend, frontend, docs site, tooling, ADR conventions (the ADR check alone, for a change to the ADRs, story cards or model that runs no tooling job), container image + smoke test, cancelling a pull request’s superseded runs, ‘CI result’), CodeQL, dependency review, Infrastructure preview (Bicep what-if), Azure OIDC check, Database migration (manual, per environment, OIDC login) and Publish docs site (trusted workflow_run publisher for production and PR previews) and Dashboard snapshot (daily and on demand: takes and checks the delivery snapshot, commits it to the dashboard-data branch, and opens or updates the threshold issues; three jobs with separate permissions, never part of CI result).ADR-0012, ADR-0013, ADR-0023, ADR-0025, ADR-0034, ADR-0045, ADR-0046
Delivery dashboard toolservice.NET 10 file-based app (tools/delivery-dashboard) that gathers delivery data from the GitHub API (CI job run times against the pinned baseline and the ADR-0045 trend verdicts, queue time, the failure rates of CI jobs and reruns, pull request and issue flow, open stacks and epic progress) into one versioned, public-safe JSON snapshot per day. It validates every snapshot against the schema and the privacy rules (aggregates and public numbers only, no paths, handles or e-mail addresses) before it is published, checks the size of the data branch against its limit, and compares the snapshot with the thresholds, opening or updating one performance issue per kind of alert and no other alert.ADR-0017, ADR-0045, ADR-0049
Dashboard data branchdata-assetThe never-merged dashboard-data branch: README.md and one JSON snapshot per day in snapshots/YYYY-MM-DD.json, committed by the daily Dashboard snapshot workflow (a second run on the same day replaces that day’s file). Every daily snapshot is kept until snapshots/ would pass 50 MB, which the workflow checks before it publishes; the runbook says how to thin it to weekly files then. It holds aggregates and public numbers only.ADR-0049
Azure Container Registrysystemcrcalendar, Basic SKU, admin user disabled. Holds the SHA-tagged calendar image; the Container App pulls with its user-assigned identity (AcrPull).ADR-0029, ADR-0034
App Key Vaultsystemkv-app-: RBAC-authorised Standard vault holding only what the running app needs: calendar-connection-string, google-client-id, google-client-secret and allowed-email-N. The Container App’s user-assigned identity has Key Vault Secrets User on this vault only; Container Apps resolves the secrets by versionless URI into environment variables.ADR-0032, ADR-0035
Ops Key Vaultsystemkv-ops-: RBAC-authorised vault for operational credentials the app never sees: the PostgreSQL administrator password, calendar-migrator-password and calendar-app-password. Read by the deployer identity (infra tool, migration workflow) only.ADR-0032, ADR-0035
Log Analytics + Application Insightssystemlaw-calendar- (PerGB2018, 30-day retention) receives Container Apps console logs and Key Vault audit events; appi-calendar- is a workspace-based Application Insights resource.ADR-0029, ADR-0032
Calendar container imagecontainerOne image built by the multi-stage Dockerfile: the pnpm build of the SPA is copied into the API’s wwwroot and published with the .NET 10 runtime image, running as a non-root user on port 8080. The same SHA-tagged image is promoted from staging to production (ADR-0030, ADR-0034).ADR-0018, ADR-0021, ADR-0030, ADR-0034
Azure Container Apps environmentsystemcae-calendar- on the Consumption workload profile hosting the single Container App ca-calendar-: external HTTPS ingress (allowInsecure: false, transport auto) to target port 8080, single active revision, min 0 / max 1 replicas, startup/liveness/readiness probes on /api/health, logs to Log Analytics.ADR-0029, ADR-0030, ADR-0032, ADR-0035
Azure resource group (per environment)systemOne resource group per environment (staging, production) in UK South, deployed with Bicep (infra/main.bicep): monitoring, foundation (registry, vaults, identity, role assignments), database and app modules. Resource groups alone are not a security boundary: identities and role assignments are scoped per environment too.ADR-0029, ADR-0033, ADR-0035
Decision log, story cards, runbooks and benchmarksdata-assetdocs/decisions (MADR 4.0 ADRs with decision drivers, star-rating tables and driver-tagged pros/cons, indexed in README.md and validated by just tools adr) and docs/stories (story cards: the long-lived source of truth for each story). Both are the input of the documentation site, together with the runbooks in docs/runbooks (indexed in order in README.md) and the benchmark records in docs/benchmarks.ADR-0000, ADR-0028
Documentation site (Calendar · Docs)webclientAstro Starlight site (frontend/apps/docs) built from the agent thoughts, the decision log, the story cards, the CALM model, the runbooks and the benchmark records; the root redirects to the first agent thought, the report on why the repository exists; each agent thought has the stable route agent-thoughts/NNNN/, each ADR adr/NNNN/, each story stories/NNNN/, each runbook runbooks//, each benchmark record benchmarks/NNNN/ and the delivery dashboard pages under dashboard/, rendered at build time from the snapshots on the dashboard-data branch. Production is published from main; docs-only pull requests from this repository (every changed file under docs/ or frontend/apps/docs/) get previews at pr-preview/pr-N/. The site holds no authentication or sensitive state.ADR-0022, ADR-0023, ADR-0025, ADR-0028, ADR-0049
GitHub PagessystemStatic hosting for the documentation site. A gh-pages state branch retains production at the root and previews under pr-preview/; only the trusted publish job (github-pages environment) has deploy permissions and publications are serialized.ADR-0023, ADR-0025
