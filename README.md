# Calendar

[![Documentation](https://img.shields.io/badge/Documentation-blue?style=flat-square&logo=readme)](https://mgasca.github.io/calendar/)

Monorepo for the Calendar application: a .NET backend and a web front end, with room for more UIs.

Create todo tasks from the calendar or **My tasks**, with optional date or exact-time deadlines, priority, and notes. Review Upcoming, Overdue, Completed, and No deadline lists. See the [task story and user guide](docs/stories/0003-add-todo-tasks.md). Apply the new migration with `just db migrate` before running an existing database.

## Layout

```
backend/                 .NET 10 solution (Calendar.slnx)
  src/Calendar.Domain/     Domain model; no framework dependencies
  src/Calendar.Infrastructure/  EF Core DbContext, mappings, migrations (PostgreSQL)
  src/Calendar.Api/        ASP.NET Core minimal API
  tests/                   xUnit v3 test projects (one per src project) + Calendar.Testing (Testcontainers support)
compose.yaml             Local backing services (PostgreSQL); init scripts in docker/postgres/init/
contracts/openapi.json   API contract, generated by the backend build — commit changes
frontend/                pnpm workspace
  apps/web/                React + Vite + TypeScript web UI
  apps/docs/               Astro + Starlight reader for ADRs, stories, the architecture model, runbooks and benchmarks
  packages/api-client/     Typed client generated from contracts/openapi.json, shared by all TS UIs
docs/architecture/       FINOS CALM model of the system, rendered as the docs site's Architecture section
docs/decisions/          Architecture Decision Records (MADR)
docs/stories/            User stories: background, decisions, implementation notes, user guide
docs/runbooks/           Operations runbooks (Azure bootstrap, infrastructure, database), rendered as the docs site's Runbooks section
docs/benchmarks/         Benchmark records, rendered as the docs site's Benchmarks section
.github/                 CI and Dependabot
```

New UIs go under `frontend/apps/` (TypeScript) or a new top-level directory for other stacks; they should consume `contracts/openapi.json`.

### One-time setup on Linux / WSL

```sh
# .NET SDK, user-local (no sudo)
curl -sSL https://dot.net/v1/dotnet-install.sh -o /tmp/dotnet-install.sh
bash /tmp/dotnet-install.sh --channel 10.0 --install-dir "$HOME/.dotnet"
echo 'export DOTNET_ROOT=$HOME/.dotnet PATH=$HOME/.dotnet:$HOME/.dotnet/tools:$PATH' >> ~/.bashrc

# Node via fnm, which reads .node-version and switches automatically on cd
curl -fsSL https://fnm.vercel.app/install | bash -s -- --skip-shell
echo 'eval "$(fnm env --use-on-cd --version-file-strategy=recursive --corepack-enabled --shell bash)"' >> ~/.bashrc
exec bash                      # reload the shell
cd calendar/frontend && fnm install && corepack enable pnpm

# just: download the release named in .just-version from the link above, then put it on PATH

./tools/doctor/doctor.sh       # everything should be ✓
```

## Documentation website

The Astro + Starlight site opens on the **Architecture** overview (`/` redirects to `/architecture/`) and renders the canonical Markdown in `docs/decisions/` (each ADR at `/adr/NNNN/`, listed with its status in the sidebar; the decision log table itself is not a page) and `docs/stories/` (the user stories, at `/stories/NNNN/`), and the FINOS CALM model in `docs/architecture/` (the **Architecture** section, at `/architecture/`: context and container diagrams, a page per component and per business flow, and the controls, all generated from the model and linked to their ADRs; see [ADR-0039](docs/decisions/0039-architecture-model-and-visualization-tooling.md)), the runbooks in `docs/runbooks/` (at `/runbooks/<name>/`, in the order of their index) and the benchmark records in `docs/benchmarks/` (at `/benchmarks/NNNN/`). Every ADR and story merged to `main` is published, including proposed and superseded decisions. Links between ADRs, stories, runbooks and benchmarks, and from any of them to the code they reference, work on the published site. Edit the sources there; generated pages are build output and are not committed.

After installing the frontend dependencies with `just frontend install`, use `just docs dev` to develop the site. `just docs build` builds and verifies the static output in `frontend/apps/docs/dist`; `just docs preview` serves that output. These tasks require Node and pnpm, but do not require the backend or database.

To reproduce the GitHub Pages project path locally:

```sh
DOCS_SITE_URL=https://mgasca.github.io/calendar/ just docs build
DOCS_SITE_URL=https://mgasca.github.io/calendar/ just docs preview
# Open http://localhost:4321/calendar/
```

`DOCS_SITE_URL` is the full public URL, including any project path. The site derives its origin and base path from this URL, so custom domains and root-hosted sites work without hard-coded `/calendar/` links. Local development defaults to the site root.

GitHub Pages uses **Settings → Pages → Build and deployment → Source: GitHub Actions**. CI builds and checks the site for pull requests, merge queues, and manual runs. Successful `main` push builds update production; successful same-repository PR builds update their preview. The separate **Publish ADR site** workflow accepts artifacts only from successful CI runs with a current source revision, then publishes through the `github-pages` environment. Keep its deployment branch rule restricted to `main`: the publisher runs trusted default-branch workflow code even when publishing PR artifacts.

The configured publication URL is [mgasca.github.io/calendar](https://mgasca.github.io/calendar/). The site becomes available after the workflow's first successful deployment from `main`; an unmerged branch or pull request does not update it.

### Pull request previews

After CI succeeds, a PR from this repository gets an **ADR preview** check and one sticky PR comment, both linking to `https://mgasca.github.io/calendar/pr-preview/pr-<number>/`. The comment is updated in place on each new preview. Each new successful revision replaces that PR's preview; closing or merging the PR removes it. Fork PRs run CI but do not publish previews. Manual CI runs and merge-queue runs do not publish either.

The publisher retains generated production files and preview directories on the `gh-pages` branch. That branch is storage for the combined artifact, **not** the Pages publishing source: leave Pages configured for GitHub Actions. A production update preserves open previews, a preview update preserves production, and queued publication serializes snapshot reads, updates, and deployment. The publisher also removes closed PR directories during subsequent publications. Do not edit the generated branch manually.

The privileged publisher downloads only static artifacts, rejects non-regular and reserved paths, and never checks out or executes PR code. It rechecks the current PR head or `main` revision before updating the snapshot. Previews share the production origin, so they are intended for trusted repository contributors; unreviewed preview JavaScript has the same origin as production documentation. No third-party hosting account or extra deployment secret is needed. See [ADR-0025](docs/decisions/0025-github-pages-pr-previews.md).

**First setup:** merge the preview infrastructure into `main` first. Its successful CI run creates the initial production snapshot. Then rerun CI by pushing a commit to the UI PR branch (or use GitHub's **Re-run all jobs** on its `pull_request` run). GitHub loads `workflow_run` automation from the default branch, so an unmerged infrastructure PR cannot enable its own preview. A preview run arriving before the first production snapshot is skipped with a notice; rerun that PR's CI after production succeeds. The preview URL appears in the PR's **ADR preview** check and publisher run summary. If the publisher fails, inspect **Actions → Publish ADR site** and rerun that workflow; do not dispatch CI manually to publish.

### Local database

```sh
just db up        # starts PostgreSQL on 127.0.0.1:5432; creates .env from .env.example on first run
just db migrate   # applies EF Core migrations as calendar_migrator
```

`.env` is untracked and holds disposable local passwords. The database creates two roles: `calendar_migrator` (owns the schema, runs migrations) and `calendar_app` (DML only; the API always connects as this role). Migrations are never applied at API startup.

Give the API its connection string with user-secrets (no secret is ever committed to `appsettings*.json`). Use the `CALENDAR_APP_PASSWORD` from your `.env`:

```sh
dotnet user-secrets set "ConnectionStrings:Calendar" \
  "Host=127.0.0.1;Port=5432;Database=calendar;Username=calendar_app;Password=dev-app-password" \
  --project backend/src/Calendar.Api
```

or set the environment variable `ConnectionStrings__Calendar`. In Development the API logs EF Core SQL commands. Integration tests need no setup beyond a running Docker daemon: they start their own throwaway PostgreSQL (the image pinned in `compose.yaml`) with `Calendar.Testing`.

> **Adding a backing service?** Re-evaluate .NET Aspire for local orchestration before wiring it into Docker Compose by hand, and add a row here. See [ADR-0016](docs/decisions/0016-local-database-provisioning.md).

### Google sign-in setup

Create a Google OAuth web application client and configure its authorized redirect URIs for each environment:

* Development: `http://localhost:5173/api/auth/callback/google`
* Production: `https://<host>/api/auth/callback/google`

Set `Auth__Google__ClientId`, `Auth__Google__ClientSecret` and indexed entries such as `Auth__AllowedEmails__0` in the untracked `.env` for local development, then export them into the API process (`just backend dev` loads `.env` for you; restart it after editing, since hot reload does not re-read the environment); use deployment secrets for production. Add only the verified Google emails permitted to access the calendar. Keep the client secret out of version control. Use HTTPS in production and configure trusted forwarded headers when behind a proxy so redirects and secure cookies use the public origin.

**Without Google, locally.** To try the web app without an OAuth client, set `Auth__AllowedEmails__0` in `.env`, replace the placeholder `Auth__DevSeedKey` there with the output of `openssl rand -hex 32` (anyone can read the one in `.env.example`), start the API with `just backend dev`, and run `just frontend dev-signed-in` instead of `just frontend dev`. The Vite proxy adds the Development-only seed key to `/api` requests from the app's own page, so http://localhost:5173 opens signed in as that email. Pages from other origins, including other `localhost` ports, get no key. The key never reaches the browser. The dev server refuses to start in three cases:
* the key is missing or shorter than 32 characters;
* `CALENDAR_API_URL` is not a loopback address;
* it's asked to listen beyond this machine (`--host`, `server.host`, or `vite preview --host`).

It warns, but starts, if the key is still the placeholder. To test from another device, use plain `just frontend dev --host`. **Sign out** does not end this mode: stop the recipe instead ([story 0021](docs/stories/0021-sign-in-locally-without-google.md), [ADR-0027](docs/decisions/0027-google-oidc-bff-session.md) amendment).

> **Authentication and limitations.** Google sign-in protects the API with a same-origin cookie ([ADR-0027](docs/decisions/0027-google-oidc-bff-session.md)). Each allowed account sees only its own events and tasks ([ADR-0041](docs/decisions/0041-per-user-data-ownership.md)): rows from before per-user ownership belong to the first email in `Auth__AllowedEmails`, which claims them at its first sign-in, and `just db seed` seeds that account. Add bearer support before enabling non-browser clients, and re-decide row-level security before sharing between users, a non-browser client with its own identity, or a background job that reads across users.

### Production environment configuration

Set `ConnectionStrings__Calendar` to the PostgreSQL connection string for the least-privilege
`calendar_app` role. Supply `Auth__Google__ClientId` and `Auth__Google__ClientSecret` from
deployment secrets, and configure allowed Google email addresses as indexed environment variables
`Auth__AllowedEmails__0`, `Auth__AllowedEmails__1`, and so on. Register the public HTTPS callback
`https://<host>/api/auth/callback/google` with Google. The API trusts one forwarded hop from the
Container Apps ingress; the container must only be reachable through that ingress.

ASP.NET Data Protection keys are stored unencrypted in the calendar database so sessions survive
restarts and revisions. Apply migrations separately as `calendar_migrator` before starting a new
revision; the application never applies them. Restrict database access and backups accordingly.

### Local container image

Run `just image build` to build `calendar:local` and `calendar:<short-git-sha>` using the Node major in `frontend/.node-version` and the pnpm version in `frontend/package.json`. The .NET SDK and runtime use the .NET 10 image family; `backend/global.json` selects the SDK. The image listens on port **8080**, which is also the Azure Container Apps target port.

Run `just db::up db::migrate` first, then `just image run`. On Linux/WSL this uses host networking to reach the loopback-only PostgreSQL port with the `calendar_app` role; port 8080 must be free and is exposed on the host network interfaces. It loads `.env` and passes the connection string through the environment. The image defaults to Production; use `just image run Development` to enable development-only behavior. Production Google sign-in requires real `Auth__Google__ClientId`, `Auth__Google__ClientSecret` and `Auth__AllowedEmails__0` settings in `.env`, otherwise only anonymous endpoints are available.

In another terminal, run `just image smoke` (optionally set `BASE_URL`) to check the SPA root, `/week` deep link, `/api/health`, unknown API 404 and anonymous protected API 401. The runtime image has no healthcheck because it does not include an HTTP client; external platforms can probe `/api/health`.
