# Azure infrastructure

Each UK South environment has its own Log Analytics workspace, workspace-based Application Insights, Basic ACR, Standard RBAC Key Vault, user-assigned identity, PostgreSQL Flexible Server and Container Apps environment and app. Tags identify the app and environment. The workload identity has AcrPull and Key Vault Secrets User; the deployment identity has Key Vault Secrets User only. Vault audit events go to Log Analytics. Resources are isolated by environment; use synthetic data in staging.

## Initial deployment

Complete [Azure bootstrap](azure-bootstrap.md), including provider registration and its capacity query. Confirm the selected Burstable SKUs are available to this subscription: staging `Standard_B1ms` is the smallest documented SKU, production `Standard_B2s` is a small SKU. Neither has been verified against this subscription. Check global resource name availability and quotas.

1. Deploy the foundation with `deployDatabaseAndApp=false`, passing the deployment service principal's **object ID** as `deployerPrincipalId`. It creates the vault and role assignments but no database or app. Wait for RBAC propagation.
2. An owner with permission to assign roles grants their own user **Key Vault Secrets Officer** on that vault. This is a separate human assignment; the deployment identity does not receive write access. Wait for propagation.
3. With the owner's Azure login, run the tooling command `secret init-postgres-password <env>`. It generates a password locally and stores it in the vault without printing it. Do not put the value in a shell argument, parameter file, log or repository.
4. Deploy with `deployDatabaseAndApp=true`. The deployment tool reads the password from the vault and passes it as the secure `postgresAdministratorPassword` parameter without logging it. Preview with what-if before applying. Repeat the sequence independently for production.

The secure parameter is used instead of a checked-in `az.getSecret()` reference: foundation must work before the vault and secret exist, while the subscription-specific vault ID is not known in the parameter files. Microsoft documents [secure deployment parameters and Key Vault references](https://learn.microsoft.com/azure/azure-resource-manager/templates/key-vault-parameter); the tool must use a protected, non-logging transport. The vault also enables template deployment for future use. Full-phase what-if and deployment need the existing password and live verification.

## Parameters and application secrets

`infra/main.bicep` is resource-group scoped. The checked-in parameter files contain the environment and SKU only. The deployment tool supplies `deployerPrincipalId`, `deployDatabaseAndApp`, `postgresAdministratorPassword`, `containerImage`, `keyVaultSecretNames`, and `allowedFirewallIps` as needed. Firewall entries are objects with `startIpAddress` and `endIpAddress`; `allowAzureServices` defaults to false. The Azure-services rule permits connections from Azure broadly, not just this subscription. Ensure the actual app and migration runner outbound IPs are allowed; dynamic outbound addresses can complicate this.

`minReplicas` and `maxReplicas` default to 0 and 1. `targetPort` defaults to 80 and `enableHealthProbes` to false for the public hello-world placeholder. When deploying the real app, set its actual listening port and enable startup, liveness and readiness HTTP probes at `/api/health`. Measure cold-start time before increasing the minimum. The app uses 0.25 vCPU and 0.5 GiB and HTTPS-only external ingress.

The `keyVaultSecretNames` list must contain only existing, enabled secrets. Versionless references use the app identity. The names `calendar-connection-string`, `google-client-id`, `google-client-secret`, and `allowed-email-0`, `allowed-email-1`, etc. map to `ConnectionStrings__Calendar`, `Auth__Google__ClientId`, `Auth__Google__ClientSecret`, and `Auth__AllowedEmails__0`, `Auth__AllowedEmails__1`, etc. Add only names whose values have been populated. Changes to references and RBAC propagation must be checked live. The initial placeholder uses an empty list.

S6 must create `calendar_migrator` and `calendar_app`, establish schema ownership and least-privilege grants as in `docker/postgres/init/01-roles.sh`, run migrations separately, and store the app connection string using the app role. S9 must provision separate Google OAuth clients, credentials and allow-listed emails in each vault and configure redirect URIs. S7 must publish and promote the real image. S8 must wire Application Insights and alerts.

## Staging database operations

Use the tooling's staging database start and stop commands, or run `az postgres flexible-server stop --resource-group rg-calendar-staging --name <server-name>` and replace `stop` with `start` before migrations, deployment or testing. Confirm state in Azure before continuing. Stopping makes staging unavailable; storage and excess backup storage remain billable. Azure automatically starts a stopped server after seven days and no new backups are taken while stopped. Monitor state and stop it again when appropriate. Burstable servers consume CPU credits above baseline; prolonged load can exhaust credits and degrade availability. Monitor credits, alert on low balance, and choose a larger SKU or tier if needed. See [compute guidance](https://learn.microsoft.com/azure/postgresql/flexible-server/concepts-compute-storage) and [stop and start](https://learn.microsoft.com/azure/postgresql/configure-maintain/how-to-stop-server).

## Estimated monthly costs

Illustrative USD retail rates queried from the [Microsoft retail prices API](https://prices.azure.com/api/retail/prices) for UK South on 2026-10-29; rates exclude tax, discounts and currency conversion. The exact meters are: Container Registry **Basic Registry Unit** $0.1666/day; PostgreSQL Flexible Server Burstable BS Series Compute **B1MS** $0.019/hour and **B2S** $0.076/hour; Flex Server Storage **Storage Data Stored** $0.133/GB-month; Flexible Server Backup Storage **Backup Storage LRS Data Stored** $0.10/GB-month; Log Analytics **Analytics Logs Data Ingestion** $2.88/GB (also a $0 free tier meter); Key Vault **Operations** $0.03/10,000 operations. These are observed retail prices, not a quote.

Assume 730 hours of compute, 30 registry days, 32 GB storage, backup usage no greater than the included provisioned storage, 1 GB ingested within the applicable free allowance, 10,000 vault operations, and Container Apps usage within the subscription's shared free grant. Under those assumptions staging is approximately **$23.15/month**, production **$64.76/month**, and both **$87.92/month**. The staging estimate assumes it runs continuously; every stopped hour saves about $0.019 in compute until automatic restart. Backup overage, extra log ingestion/retention, request or compute overages, network, taxes and other services add cost. Verify applicable allowances, actual usage and invoices: the estimate is not a spending cap. Container Apps grant assumptions are detailed in [ADR-0029](../decisions/0029-azure-container-apps-compute-platform.md).
