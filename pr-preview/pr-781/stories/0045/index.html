0045 · Resolve the ADR sweep findings of 2026-11-07

Status: implemented · Date: 2026-11-07 · Issue #474 · PR #490 · PR #505 · PR #506 · PR #504 · PR #510 · PR #509 · PR #508 · PR #507 · PR #503 · PR #502 · PR #511 · PR #520 · PR #524

ADRs: ADR-0000 · ADR-0002 · ADR-0003 · ADR-0011 · ADR-0014 · ADR-0019 · ADR-0021 · ADR-0025 · ADR-0026 · ADR-0029 · ADR-0030 · ADR-0031 · ADR-0032 · ADR-0035 · ADR-0037 · ADR-0045 · ADR-0048

Story

As the maintainer, I need every finding of the 2026-11-07 ADR sweep to end in an explicit, evidenced disposition, so that the decision log says what the repository actually does without my decisions being changed or made implicitly.

Tracked in issue #474, part of epic #473. Card PR: #490.

Background

The ADR sweep of 2026-11-07 (the adr-sweep skill) audited origin/main at 52c667e6586bf950f135f119cad9eb08477d36f0. All 49 ADRs passed just tools adr. The titles and statuses in the architecture model matched. There were no proposed records and no ADR-number collisions between open PRs, and all 50 external More Information URLs returned HTTP 200. The judgement review was selective. Live cloud, account and pricing checks were not performed, so this story covers the reported findings. It does not claim that the whole decision log has been verified.

The sweep reported one finding to fix now, four grouped findings to decide (seven records) and four to watch. A Watch finding is a question that needs evidence, not a proven defect. Epic #473 tracks each finding to a disposition. The maintainer answered every question on the child issues on 2026-11-07. This card records those answers so that they outlive the issues.

The earlier mechanical sweep, epic #437, is closed. Its approved convention for inline, dated amendments is reused here and not reopened. 0010 is the earlier story that swept proposed ADRs to a decided status. This story follows the same pattern: one PR per ADR, so that each record is reviewed and merged on its own.

Agreed scope

  • This card first (PR 0): a docs-only card with the scope, the dispositions and the delivery forecast, before any delivery PR of the epic (#474).
  • Dated amendments that retain the decision (#475 to #481): each of ADR-0048, 0002, 0003, 0026, 0030, 0021 and 0045 gets a dated amendment under the amendment convention of #437. The decision is retained, and there is no re-rating, because no driver or weight changed. Status and title do not change, so the architecture model does not change either.
    • ADR-0048 (#475): correct the consequence that says Dependabot does not watch the frontend. .github/dependabot.yml has an npm entry for /frontend, and ADR-0012 records that coverage. Fontsource is retained.
    • ADR-0002, 0003, 0026 and 0030 (#476 to #479): record the delivery of the single-container SPA hosting follow-up. The API serves static files and the SPA fallback (backend/src/Calendar.Api/Program.cs, UseStaticFiles and MapFallback), and container PR #114 has merged. Each amendment links the exact test and PR evidence. It keeps tests that were run apart from checks that only a deployment can make, and claims no live Azure verification. The decision-time context is kept as it was written. Requirements that are only partly tested (asset 200 and body, the problem-details body, 403, the HttpOnly and SameSite cookie flags) are named as such in ADR-0026 and ADR-0030, which link follow-up #497 for their tests.
    • ADR-0021 (#480): the “revisit when accounts exist” trigger has fired, because ADR-0041 delivered per-user ownership. The amendment records that the trigger fired and that mandatory, explicit today and timeZone are retained, with no stored preferred zone. No product or API change.
    • ADR-0045 (#481): record the accepted exception to the 1 % false-failure budget. The back-test in record 0014 measured 5.5 % (4 of 73 runs, one-sided 95 % upper bound 12.1 %), which the maintainer accepted on 2026-11-07. The amendment links #421 and states that the review window ends at 2026-11-14 13:52Z. The method and the constants are unchanged.
  • Pages deployment collision (#429): fixed within this epic, by its own worker and PR. The worker posts the design on #429 before implementing. #429 stays the one defect issue; no duplicate is opened.
  • Historical story citations (#484): stories 0001, 0003, 0004, 0005, 0011, 0014 and 0017 cite the superseded ADR-0011, 0014 or 0019. Each card gets one recorded disposition: historical, explicitly retained, or misleading as a current rule. History is preserved, and so are the engine rules of ADR-0014 that ADR-0037 expressly retains. A card is clarified only where a citation reads as a current rule and is wrong. Old ADR numbers are not replaced mechanically. The review found two such lines, one each in 0001 and 0003 (see “Dispositions”), which one docs PR clarifies.
  • Dispositions recorded in this card alone (#482 and #483): these two need no ADR PR. Their whole scope is the disposition recorded under “Dispositions”, so this card’s PR closes them.
  • Existing work recorded, not redone (#468): the ADR-0000 Confirmation correction was delivered by PR #469 before this card.
  • Close-out: the Card worker of epic #473 owns the final update of this card: status, the pr list, the evidence links of each delivery PR, and the lessons learned.

Not in this story

  • Changing any decision or its rating. A changed decision is a new or superseding ADR (adr-draft) under its own issue, after the maintainer approves new drivers or weights.
  • Product, API or runtime hosting changes. Neither a stored time zone (#480) nor any change to SPA hosting is in scope.
  • Measuring or recalibrating the CI run-time gate. #421 keeps the week-later measurement and any recalibration. Nothing here dispatches CI, rewrites the baseline or changes the method before the review window ends.
  • Deployment work, cloud operations or spending. These stay with #79 to #83 and the deployment plan #85.
  • Migrating the preview publisher, or creating a Cloudflare account (#483).
  • Editing ADR-0025, 0029, 0031, 0032 or 0035 in this epic.
  • Rewriting decision history in ADRs or story cards.
  • The rest of the decision log. This story resolves the reported findings only.
  • New hosting tests. The partly tested hosting requirements moved to #497.

Dependencies

  • Every delivery PR (#475 to #481, #484 and #429) opens after this card merges, as epic #473 orders.
  • #421 keeps its own review date (2026-11-14) and does not gate this story.

The Pages deployment fix (#429)

  • Cause (from the design on #429): the #339 override of GITHUB_SHA never took effect, because the runner ignores GITHUB_* variables set in a step’s env. actions/deploy-pages therefore sent main’s head SHA as the build version, so every publication between two merges reused one Pages deployment ID. The first deployment of a new version was then refused with “in progress deployment” of the reused one (measured over 164 deploy steps; the mechanism is inferred, not confirmed by GitHub).
  • #504: replaced actions/deploy-pages with an inline actions/github-script Pages API step and sent a synthesized SHA-1 per run as pages_build_version. Every deploy then failed with 404. Pages appears to require the build version to be a real commit of the repository; this is inferred from the failures, and GitHub does not document it.
  • #511: reverted #504. Publishing was restored: Publish ADR site run 42422434576 succeeded.
  • #520: each publication creates its own gh-pages commit (git commit --allow-empty) and sends that commit as the build version. If Pages answers 404 for it, the step retries with GITHUB_SHA and logs a warning (fallback approved by the maintainer). An in-progress deployment is retried for up to 10 minutes, inside a deploy job timeout of 25 minutes.
  • Live verification (measured, one run): Publish ADR site run 42423849216, the first on the new workflow, created and completed Pages deployment edf6b0b49bac74160d79f25da1071152715ca069. That is a gh-pages commit, not the head of main (145105bc0 at the time), and the run logged no 404 and no fallback warning. Pages refused it 10 times with “in progress deployment” of 5eaf27b1…, a deployment from the old shared-ID workflow, and it succeeded after about 7 minutes through the retry backstop.
  • Not yet measured: whether collisions stay absent over time. Only one deploy had run on the new workflow at close-out.

Lessons learned, known issues and follow-ups

  • A fake API that accepts anything proves little. The #504 tests used a fake Pages API that accepted any build version, so they passed while the real API rejected every deploy. #520 made the fake reject versions that are not commits, as the real one does.
  • The Pages deploy step cannot run before merge. The workflow_run and pull_request_target triggers run the workflow from main, so a change to the deploy job is first exercised by the run after it merges. Plan a fast revert path (as #511 was) for such changes.
  • The runner ignores GITHUB_* overrides in a step’s env. That is why the #339 fix never worked. Pass a value under another name instead.
  • Follow-up #497: tests for the SPA hosting requirements that are only partly tested today (asset 200 and body, the problem-details body, 403, HttpOnly and SameSite). ADR-0026 and ADR-0030 link it.
  • Follow-up #421: the week-later review of the CI run-time gate stays open, with its window ending 2026-11-14 13:52Z.
  • Deferred, #482: the Azure assumptions of ADR-0029, 0031, 0032 and 0035 are revisited at the first deployment (#79 to #83, #85).
