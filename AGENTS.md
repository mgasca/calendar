# AGENTS.md

Guidance for AI coding agents (Claude Code, Codex, Cursor, …) working in this repository. Area practice lives in `backend/AGENTS.md` and `frontend/AGENTS.md`: read the one for the stack you touch (Claude Code loads it when you read or edit a file there; other agents read it natively). Rules marked *(hook)* are also enforced for Claude Code by `tools/agent-hooks` (ADR-0042); other agents follow them by hand. During the Claude-first period of ADR-0044 (`docs/decisions/0044-claude-first-agent-automation.md`), automation under `.claude/` and `tools/agent-hooks` may be Claude Code only; the guidance files stay readable by every agent.

## Overview

"Calendar": a monorepo with a .NET 10 backend (`backend/`, solution `Calendar.slnx`) and a pnpm/React/Vite/TypeScript frontend (`frontend/`). The API serves events, tasks, day and week agendas, and Google sign-in (cookie session, allow-listed emails), backed by PostgreSQL. The web app shows day, week and task views. Product stories live in `docs/stories/`, decisions in `docs/decisions/` (ADRs): read the relevant ADR before changing tooling, layout, dependencies or API conventions, and never contradict an accepted one (supersede it instead). Linux/WSL only. Toolchain pins: .NET SDK from `backend/global.json` (10.0.300 or later for the repo tools), Node from `frontend/.node-version`, pnpm via Corepack; `just doctor` verifies them. `.plan/` and `.env` are git-ignored.

## Commands

`just` (minimum version in `.just-version`) is a thin task runner over native tooling; `just` alone lists the recipes. The root holds those that span stacks: `setup`, `build`, `test`, `lint`, `check` (everything CI runs), `format`, `clean`, `contracts`, `doctor`. The rest live in modules, called as `just <module> <recipe>` (ADR-0038 amendment): `backend` (`dev` on http://localhost:5041, `test`), `frontend` (`dev`, which proxies `/api`, `test-web`), `docs` (`dev`, `build`, `test`, `architecture`, `bench`), `db` (`up`, `migrate`, `seed`, `psql`, `reset`, `down`), `image`, `infra` and `tools` (`test`, `versions`, `adr`). A module file sits beside the code it runs (`backend/mod.just`, `infra/mod.just`, …) or beside the root `justfile` (`db.just`, `image.just`) and sets its own `set shell`, because modules inherit no settings.

- `just contracts` rebuilds the API and regenerates `contracts/openapi.json` and the TS client. Commit the result: CI fails on a stale contract, and generated files are never edited by hand *(hook)*.
- Migrations are applied only by `just db migrate`, as `calendar_migrator`, never by the app (ADR-0015). The `db` recipes and `compose.yaml` address one shared Compose project (`calendar`, volume `calendar-pgdata`, port 5432) from every checkout *(hook)*; see "Working on several changes at once".
- To run several recipes of one module in order, use `run`: `just backend run build test` stops at the first failure, and words from the first one that starts with `-` go to the last recipe (`just backend run build test --filter-method "*Name*"`), and so do the words after a `--` (`just infra run what-if -- staging`). Write `-n` after `run` to preview (`just db run -n up migrate`). Without `run`, only the first word is looked up in the module (`just backend build test` runs the **root** `test`), and the `module::recipe` form (`just db::up db::migrate`) works only when no recipe but the last takes arguments.
- `just docs bench` runs the docs benchmark by hand (results in `docs/benchmarks/`); it is never part of `just test` or CI.

## Architecture

- **Contract-first across stacks**: the backend build generates `contracts/openapi.json`; `frontend/packages/api-client` generates a typed client from it (`schema.gen.ts`), shared by all TS UIs. Any new UI consumes the contract, not backend code.
- **Backend**: `Calendar.Domain` (no framework dependencies; time-zone and day rules in `Time/` and `Agenda/DayInclusion`) ← `Calendar.Infrastructure` (EF Core code-first on PostgreSQL, ADR-0014/0015; SQL forms of the domain rules in `Queries/`) ← `Calendar.Api` (minimal API; `Endpoints/`, `Contracts/`). The app connects as the least-privilege `calendar_app` role. Agenda reads are one read-only snapshot (ADR-0020). The client supplies `today` and `timeZone`; the server never decides what day it is (ADR-0021). Every endpoint requires an authenticated user except health and sign-in (ADR-0027). Tests: one xUnit project per src project plus `Calendar.Testing` (Testcontainers PostgreSQL); API tests need Docker.
- **Dependencies**: NuGet Central Package Management (`backend/Directory.Packages.props`) with a `packages.lock.json` per project, restored with `--locked-mode` in CI, so commit lock-file changes. Warnings are errors; Roslyn and Sonar analyzers run at build time.
- **Frontend**: `frontend/apps/web` (feature folders `features/day`, `week`, `tasks`, `agenda`; TanStack Router (ADR-0026) and Query; Vitest, Testing Library, MSW), `frontend/apps/docs` (Astro Starlight site), `frontend/packages/api-client`. TypeScript 6.0 and ESLint 9 are pinned (ADR-0010).
- **Repo tooling** (ADR-0017): .NET 10 file-based apps in `.claude/skills/<skill>/` or `tools/<name>/`, each with analyzers and xUnit tests run by `just tools test`; `tools/doctor/doctor.sh` is the one shell exception. Never write tooling in Python, Node or shell. Read `tools/README.md` before writing or fixing a tool.
- **Docs site and architecture model**: the site is built from `docs/agent-thoughts`, `docs/decisions`, `docs/stories`, `docs/architecture`, `docs/runbooks` and `docs/benchmarks`. Each folder's `README.md` holds conventions only. The site discovers documents from the filesystem and reads metadata from each file; invalid metadata, duplicate identifiers and links to unpublished documents fail the build. `docs/architecture/calendar.architecture.json` is a FINOS CALM model (ADR-0039): when you add a component, endpoint, Azure resource or ADR, or change an ADR's status, update it in the same PR.
- **ADRs**: MADR with decision drivers and a star-rating table, validated by `just tools adr` and written with the `adr-draft` skill; the `adr-sweep` skill finds the records the validator cannot fault but that drifted (status, model entry, citations, claims). Status follows the decision, not delivery: an ADR becomes `accepted` when the user approves it, in the same PR before it merges, never waiting for the implementation.

## Stories and issues

- **The card is the source of truth.** Issues drive the work; the durable record is the card in `docs/stories/` (`README.md`, `story-template.md`, the `story-draft` skill). A story that starts as an issue begins with PR 0, a docs-only card (`Refs #N`); delivery PRs follow; the PR that completes the card carries `Closes #N` *(hook)*. Base each branch on fresh `origin/main`, or stack it until its base merges.
- **Keep the decision trail on the issue**: post the concrete design before implementing, record answered questions and deferrals there, and re-read the comments before starting. One issue per defect and one PR per issue; labels per `gh label list` (`performance`: slow or wasteful; `bug`: wrong). Compare the files each branch touches; merge self-contained fixes first and wide refactors last.
- **Verify delivery across a merge**: re-read the PR state and head before adding work to a reviewed branch; once it has merged, start a new branch and PR from `origin/main` (pushing the old branch adds nothing, #180/#186) *(hook)*. Check the intended content on `main`, not commit hashes (squash merges change identity), confirm the checks passed for the delivered revision and the issue has no remaining scope, then update card and issue. Merge only when the user has authorized it.
- Never hard-code the set of stories in tests; derive it from `docs/stories/`.

## Working on several changes at once

- Give each branch its own `git worktree` from fresh `origin/main`; never edit the main checkout. Each worktree needs its own `just frontend install` (`pnpm install --frozen-lockfile` in `frontend/`).
- Worktrees do not isolate running services: `just db` recipes from any checkout hit the shared Compose project, volume and port *(hook)*. For concurrent runtime work use the throwaway stack in the `run-calendar` skill (PostgreSQL 55432, API 55041, Vite 55173), record which resources belong to the task, and before any reset, down or kill verify that the container, volume or PID is yours. Keep the ordinary defaults unchanged (ADR-0016).
- Two branches that each add an EF migration conflict in `CalendarDbContextModelSnapshot.cs`: stack the second on the first (`--base <first-branch>`) and retarget it to `main` after the first merges. Postpone a change that rewrites code several open PRs touch until they merge, and say so on its issue.
- Breaking contract changes (e.g. a list becoming `{ items, nextCursor }`) go in one PR with the regenerated `openapi.json`, the TS client and every consumer updated; find consumers with a grep for the path across `frontend/`, including MSW handlers in tests.

## Testing principles

- **Report what verification covered**: the revision (or precisely described tree), command, effective configuration and files included; distinguish local passes, skipped checks and CI results on the current head; rerun after a restore, conflict resolution or any later edit. Never generalise one passing suite into "all checks passed".
- **Preserve the fix when proving a regression test**: before removing a fix for a negative control, save the exact intended contents or patch outside the checkout, or run the control in a scratch worktree. Never `git checkout --` or `git restore` an unstaged implementation *(hook)*: it restores the committed baseline and can discard the fix (#189). Restore the saved version, inspect the diff, rerun the checks, then commit.
- **Every fix needs a test that fails without it**, confirmed against the old code. Say whether a performance finding is measured or inferred, and keep the evidence for a decision not to optimise in the story card (`docs/benchmarks/README.md` for a repeatable benchmark). A `performance` issue closes on evidence, as that README's "Performance issues" says.
- **Reviewer subagents** (`.claude/agents/`), on request: `performance-reviewer` reviews a branch for performance, `security-reviewer` for security and privacy, `delivery-performance-reviewer` does the static pass of the `delivery-performance-review` skill (CI, recipes, tests and agent loops, from history rather than a diff); other agents can follow them by hand.
- **Sandboxed agents** may lack network or Docker: restore offline with `just backend restore -p:NuGetAudit=false`, run what can run (build, format, domain and pure unit tests), state exactly which suites did not run, and never report a change as verified when its integration tests were skipped.

## Public GitHub posts

Before posting an issue, PR or comment, check the rendered text for private session/task/subagent handles and absolute machine paths; use repository-relative paths and public issue/PR links *(hook)*. If a disclosure slips through, edit the post in place. Images for a post go on the `screenshots` branch, one directory per issue or PR number, linked by commit (the `github-screenshots` skill). Issue-driven handovers (watching an issue and its PRs, questions as PR comments, resume and close-out) are opt-in via the `issue-handover` skill.
