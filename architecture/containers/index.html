Elements

ElementTypeOwnershipDescription
Calendar useractorPersonA person whose verified Google email is on the allow-list. Uses the web app in a browser to see today and the week, add events and tasks, tick tasks off and triage overdue tasks.
Maintainer / operatoractorPersonThe repository owner who merges pull requests, deploys infrastructure with the infra tool, initialises secrets and roles, runs database migrations and approves production deployments.
Google Identity (OpenID Connect)systemExternal service we only useExternal identity provider. The API runs the OpenID Connect authorization-code flow against it; the browser is redirected to Google to sign in and back to the API callback with a code.
Calendar web appwebclientBuilt in this repositoryReact 19 + Vite + TypeScript single-page app (frontend/apps/web). TanStack Router with code-based routes for /, /day/$date, /week, /week/$weekStart, /tasks, /triage and /signin; TanStack Query for server state. Reads the browser’s IANA time zone and local date and sends them with every agenda request. Served as static files from the API container (same origin, no CORS).
@calendar/api-clientlibraryBuilt in this repositoryTypeScript package (frontend/packages/api-client) generated from contracts/openapi.json with openapi-typescript; createApiClient wraps openapi-fetch with the typed paths. schema.gen.ts is never hand-edited. Shared by every TypeScript UI so that no UI depends on backend code.
@calendar/themelibraryBuilt in this repositoryTypeScript and CSS package (frontend/packages/theme) shared by the web app and the documentation site: the semantic colour tokens for the light and dark themes, selected by a data-theme attribute with a prefers-color-scheme fallback (tokens.css), the self-hosted Fontsource variable fonts (fonts.css), and the stored theme choice (THEME_STORAGE_KEY, isThemeChoice). Its tests check token contrast and that no colour literal escapes the token layer.
OpenAPI contractdata-assetBuilt in this repositorycontracts/openapi.json: the committed OpenAPI 3 document emitted by the API build. It is the single contract between the backend and every client; CI fails when it is stale.
Calendar APIserviceBuilt in this repositoryaxum API in Rust (backend/crates/calendar-api) with a framework-free calendar-domain crate (time-zone and day-inclusion rules) and calendar-infrastructure (Diesel over diesel-async on tokio-postgres, SQL forms of the domain rules). Serves events, tasks, day and week agenda read models and Google sign-in with a cookie session; also serves the SPA’s static files and index.html fallback. Every endpoint requires an authenticated user except health and sign-in.
Calendar container imagecontainerBuilt in this repositoryOne image built by the multi-stage Dockerfile: the pnpm build of the SPA is copied into the API’s wwwroot beside the calendar-api and calendar-migrate binaries on a distroless base image, running as a non-root user on port 8080. The same SHA-tagged image is promoted from staging to production (ADR-0030, ADR-0034).
Azure Container Apps environmentsystemHosting and tooling we configurecae-calendar- on the Consumption workload profile hosting the single Container App ca-calendar-: external HTTPS ingress (allowInsecure: false, transport auto) to target port 8080, single active revision, min 0 / max 1 replicas, startup/liveness/readiness probes on /api/health, logs to Log Analytics.
Calendar database (PostgreSQL 18)databaseBuilt in this repositoryThe ‘calendar’ PostgreSQL database: users (keyed by Google’s subject), events (owned by a user, with generated tstzrange/daterange spans and GiST indexes), tasks (owned by a user, with partial B-tree indexes led by owner_id for due and open-overdue lookups) and the session key (session_keys). Locally postgres:18.6-alpine in Docker Compose on 127.0.0.1:5432; in Azure a Flexible Server (Burstable Standard_B1ms, 32 GB, TLS required) per environment.
Database migratorserviceBuilt in this repositoryThe only path that changes the schema: the calendar-migrate binary (backend/crates/calendar-migrate) applies the embedded SQL migrations as calendar_migrator, in one transaction under an advisory lock; on a database EF Core migrated it first records those migrations as applied. Locally just db migrate; in Azure just infra migrate <env> builds the binary and runs it, from the manually dispatched ‘Database migration’ GitHub Actions workflow. A failed run leaves the existing revision serving.
Infrastructure toolserviceBuilt in this repository.NET 10 file-based app (tools/infra) driven by the just infra module: just infra what-if and just infra deploy <env> [foundation|full] run the Bicep deployment with the Azure CLI, just infra secret-init stores the PostgreSQL admin password in the ops vault, just infra init-roles creates the database roles, just infra db-stop and db-start manage the staging server. Pinned Azure CLI and Bicep versions are verified by just doctor.
GitHub Actions (CI/CD)serviceHosting and tooling we configureWorkflows in .github/workflows: CI (a Changes job that decides from the changed paths which jobs a pull request or merge group needs; backend, frontend, docs site, tooling, ADR conventions (the ADR check alone, for a change to the ADRs, story cards or model that runs no tooling job), container image + smoke test, cancelling a pull request’s superseded runs, ‘CI result’), CodeQL, dependency review, Infrastructure preview (Bicep what-if), Azure OIDC check, Database migration (manual, per environment, OIDC login) and Publish docs site (trusted workflow_run publisher for production and PR previews) and Dashboard snapshot (daily and on demand: takes and checks the delivery snapshot, commits it to the dashboard-data branch, and opens or updates the threshold issues; three jobs with separate permissions, never part of CI result).
Azure Container RegistrysystemHosting and tooling we configurecrcalendar, Basic SKU, admin user disabled. Holds the SHA-tagged calendar image; the Container App pulls with its user-assigned identity (AcrPull).
App Key VaultsystemHosting and tooling we configurekv-app-: RBAC-authorised Standard vault holding only what the running app needs: calendar-connection-string, google-client-id, google-client-secret and allowed-email-N. The Container App’s user-assigned identity has Key Vault Secrets User on this vault only; Container Apps resolves the secrets by versionless URI into environment variables.
Ops Key VaultsystemHosting and tooling we configurekv-ops-: RBAC-authorised vault for operational credentials the app never sees: the PostgreSQL administrator password, calendar-migrator-password and calendar-app-password. Read by the deployer identity (infra tool, migration workflow) only.
Log Analytics + Application InsightssystemHosting and tooling we configurelaw-calendar- (PerGB2018, 30-day retention) receives Container Apps console logs and Key Vault audit events; appi-calendar- is a workspace-based Application Insights resource.
Azure resource group (per environment)systemHosting and tooling we configureOne resource group per environment (staging, production) in UK South, deployed with Bicep (infra/main.bicep): monitoring, foundation (registry, vaults, identity, role assignments), database and app modules. Resource groups alone are not a security boundary: identities and role assignments are scoped per environment too.
Decision log, story cards, runbooks and benchmarksdata-assetBuilt in this repositorydocs/decisions (MADR 4.0 ADRs with decision drivers, star-rating tables and driver-tagged pros/cons, indexed in README.md and validated by just tools adr) and docs/stories (story cards: the long-lived source of truth for each story). Both are the input of the documentation site, together with the runbooks in docs/runbooks (indexed in order in README.md) and the benchmark records in docs/benchmarks.
Documentation site (Calendar · Docs)webclientBuilt in this repositoryAstro Starlight site (frontend/apps/docs) built from the agent thoughts, the decision log, the story cards, the CALM model, the runbooks and the benchmark records; the root redirects to the first agent thought, the report on why the repository exists; each agent thought has the stable route agent-thoughts/NNNN/, each ADR adr/NNNN/, each story stories/NNNN/, each runbook runbooks//, each benchmark record benchmarks/NNNN/ and the delivery dashboard pages under dashboard/, rendered at build time from the snapshots on the dashboard-data branch. Production is published from main; docs-only pull requests from this repository (every changed file under docs/ or frontend/apps/docs/) get previews at pr-preview/pr-N/. The site holds no authentication or sensitive state.
GitHub PagessystemHosting and tooling we configureStatic hosting for the documentation site. A gh-pages state branch retains production at the root and previews under pr-preview/; only the trusted publish job (github-pages environment) has deploy permissions and publications are serialized.
Delivery dashboard toolserviceBuilt in this repository.NET 10 file-based app (tools/delivery-dashboard) that gathers delivery data from the GitHub API (CI job run times against the pinned baseline and the ADR-0045 trend verdicts, queue time, the failure rates of CI jobs and reruns, pull request and issue flow, open stacks and epic progress) into one versioned, public-safe JSON snapshot per day. It validates every snapshot against the schema and the privacy rules (aggregates and public numbers only, no paths, handles or e-mail addresses) before it is published, checks the size of the data branch against its limit, and compares the snapshot with the thresholds, opening or updating one performance issue per kind of alert and no other alert.
Dashboard data branchdata-assetBuilt in this repositoryThe never-merged dashboard-data branch: README.md and one JSON snapshot per day in snapshots/YYYY-MM-DD.json, committed by the daily Dashboard snapshot workflow (a second run on the same day replaces that day’s file). Every daily snapshot is kept until snapshots/ would pass 50 MB, which the workflow checks before it publishes; the runbook says how to thin it to weekly files then. It holds aggregates and public numbers only.
