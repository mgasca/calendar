Controls

The non-functional requirements the model records as CALM controls, and the elements each applies to. Each control names a requirement schema (a JSON Schema in docs/architecture/controls/) and carries an inline configuration that conforms to it; the configuration is shown on the element or flow page.

accessibility

Requirement schema: https://raw.githubusercontent.com/mgasca/calendar/main/docs/architecture/controls/accessibility.requirement.json

  • Calendar web app: Accessibility and usability acceptance criteria shared by the story cards: keyboard operation, native modal dialogs with focus management, status messages for assistive tech, overdue conveyed in text as well as colour, and usable loading/empty/error states on a phone.

authentication

Requirement schema: https://raw.githubusercontent.com/mgasca/calendar/main/docs/architecture/controls/authentication.requirement.json

  • Calendar API: Google OpenID Connect with a backend-for-frontend cookie session (ADR-0027). The fallback authorization policy requires an authenticated user on every endpoint; only health, the sign-in endpoints and the SPA static files are anonymous. Only verified emails on the allow-list may sign in.
  • Flow Google sign-in: The flow must leave no session for a non-allow-listed or unverified email and must never follow a non-local return URL.

client-performance

Requirement schema: https://raw.githubusercontent.com/mgasca/calendar/main/docs/architecture/controls/client-performance.requirement.json

  • Calendar web app: Rules from the frontend performance review (issues #42–#49): cache server state for 30 s, refetch agendas every 5 minutes and on focus/visibility/midnight, update task toggles optimistically with per-task rollback, cache Intl formatters, subscribe to the clock only in the smallest component, and prove every performance fix with a test that fails without it.

concurrency-control

Requirement schema: https://raw.githubusercontent.com/mgasca/calendar/main/docs/architecture/controls/concurrency-control.requirement.json

  • Calendar API: Writes use optimistic concurrency on the PostgreSQL xmin system column (ADR-0015) and report conflicts as 409. Set-based bulk actions on ‘all N overdue’ run in a SERIALIZABLE transaction guarded by the client’s expected count.
  • Flow Tick a task off (optimistic): Conflicting toggles are detected by xmin and reconciled by a refetch rather than overwritten.
  • Flow Triage all overdue tasks: ‘All N overdue’ must never act on a different set than the person saw.

contract-first

Requirement schema: https://raw.githubusercontent.com/mgasca/calendar/main/docs/architecture/controls/contract-first.requirement.json

  • The whole system: The OpenAPI document is the contract between the backend and every UI. The API build writes it, CI fails when the committed copy is stale, and the TypeScript client is generated from it and never hand-edited (ADR-0004).

data-durability

Requirement schema: https://raw.githubusercontent.com/mgasca/calendar/main/docs/architecture/controls/data-durability.requirement.json

  • Calendar database (PostgreSQL 18): Managed backups with 7-day point-in-time retention in Azure, TLS-only transport, a narrow firewall, and database-level integrity constraints that mirror the domain rules (ADR-0014, ADR-0031).

delivery-performance

Requirement schema: https://raw.githubusercontent.com/mgasca/calendar/main/docs/architecture/controls/delivery-performance.requirement.json

  • GitHub Actions (CI/CD): How long CI may make an author wait (ADR-0045, epic #380): each gated job of ci.yml fails a pull request when it is clearly slower than its pinned baseline, a daily trend check on main reports smaller slowdowns as one issue, and mechanism guards fail when the cause of a fixed slowdown (#272, #347, #368) comes back. The control points to the thresholds in .github/ci-baseline.json; it never copies them.

environment-separation

Requirement schema: https://raw.githubusercontent.com/mgasca/calendar/main/docs/architecture/controls/environment-separation.requirement.json

  • The whole system: Staging and production are separate Azure resource groups with their own Container App, PostgreSQL server, Key Vaults, Google OAuth client, allow-list and deployment identity. Staging holds synthetic data only (ADR-0035).

least-privilege-data-access

Requirement schema: https://raw.githubusercontent.com/mgasca/calendar/main/docs/architecture/controls/least-privilege-data-access.requirement.json

  • Relationship api-reads-writes-db: Calendar API → Calendar database (PostgreSQL 18): The app always connects as calendar_app, which can only read and write rows in the tables the migrator created. It cannot change the schema, and the app never applies migrations (ADR-0014, ADR-0015, ADR-0031).
  • Relationship migrator-migrates-db: Database migrator → Calendar database (PostgreSQL 18): Only calendar_migrator owns the schema and runs DDL. Migrations run as a separate, idempotent step before traffic shifts, never inside the app (ADR-0015, ADR-0034).
  • Flow Apply database migrations to an environment: Schema changes happen only through this path and only as the schema owner.

observability

Requirement schema: https://raw.githubusercontent.com/mgasca/calendar/main/docs/architecture/controls/observability.requirement.json

  • Calendar API: The container exposes /api/health for startup, liveness and readiness probes; console logs and probe results go to the Log Analytics workspace, and Application Insights is provisioned in the same workspace.

per-user-data-isolation

Requirement schema: https://raw.githubusercontent.com/mgasca/calendar/main/docs/architecture/controls/per-user-data-isolation.requirement.json

  • Calendar API: Every event and task belongs to one user (owner_id). CalendarDbContext applies a global query filter keyed by the signed-in user, so every read, count, ExecuteUpdate and ExecuteDelete is scoped by default; a context with no user sees nothing; another user’s id answers 404 (ADR-0041).

quality-gates

Requirement schema: https://raw.githubusercontent.com/mgasca/calendar/main/docs/architecture/controls/quality-gates.requirement.json

  • The whole system: Every change passes the same gates locally (just check) and in CI: analyzers with warnings as errors, formatting, type-aware lint, tests, the EF model/migrations check, the contract check, the tooling tests and the ADR conventions check. The single required status check on main is ‘CI result’ (ADR-0009, ADR-0012, ADR-0036).

query-performance

Requirement schema: https://raw.githubusercontent.com/mgasca/calendar/main/docs/architecture/controls/query-performance.requirement.json

  • Calendar database (PostgreSQL 18): Index design from the backend performance review (issues #50–#55): partial indexes for open/dated tasks, GiST range indexes for overlap queries, disjoint UNION ALL branches so partial indexes apply, and measured EXPLAIN (ANALYZE, BUFFERS) plans in every query PR.

read-consistency

Requirement schema: https://raw.githubusercontent.com/mgasca/calendar/main/docs/architecture/controls/read-consistency.requirement.json

  • Calendar API: Every agenda read (day or week) is one read-only REPEATABLE READ snapshot, so a task completed or an event added between its queries cannot appear in some lists and not others (ADR-0020). The week endpoint reuses the same range-based builder with the same fixed number of queries (ADR-0024).
  • Flow View today’s agenda: One snapshot per agenda read so lists never disagree with each other.

request-limits

Requirement schema: https://raw.githubusercontent.com/mgasca/calendar/main/docs/architecture/controls/request-limits.requirement.json

  • Calendar API: All input is validated into RFC 9457 problem details with per-field errors; list endpoints use opaque keyset cursors with bounded page sizes; bulk requests are capped.
  • Flow Triage all overdue tasks: Bulk and paging limits that bound a triage request.

secrets-management

Requirement schema: https://raw.githubusercontent.com/mgasca/calendar/main/docs/architecture/controls/secrets-management.requirement.json

  • App Key Vault: Secrets live only in Azure Key Vault and reach the container as Key Vault references resolved through a user-assigned managed identity; nothing secret is in source, Bicep, parameters, logs or workflow output (ADR-0032, ADR-0033).

supply-chain-integrity

Requirement schema: https://raw.githubusercontent.com/mgasca/calendar/main/docs/architecture/controls/supply-chain-integrity.requirement.json

  • The whole system: Builds are reproducible from pinned toolchains and lock files, base images and third-party actions are pinned by digest or SHA, dependency updates are automated, and deployment uses OIDC federation rather than long-lived credentials (ADR-0006, ADR-0010, ADR-0012, ADR-0034).

time-correctness

Requirement schema: https://raw.githubusercontent.com/mgasca/calendar/main/docs/architecture/controls/time-correctness.requirement.json

  • Calendar API: The client’s IANA time zone and local date define the day; the server never decides what day it is (ADR-0021). Instants are UTC DateTimeOffset with an end-exclusive span plus the IANA zone id, all-day values are end-exclusive floating dates, and DST gaps and overlaps are handled in one place (ADR-0018).
  • Flow View today’s agenda: The day shown is the client’s local day in the client’s zone; the server only computes the window.

transport-security

Requirement schema: https://raw.githubusercontent.com/mgasca/calendar/main/docs/architecture/controls/transport-security.requirement.json

  • Relationship web-app-calls-api: Calendar web app → Calendar API: Same-origin HTTPS only: the Container Apps ingress terminates TLS and refuses plain HTTP, the API adds HSTS and HTTPS redirection outside Development, trusts X-Forwarded-* only from the ingress, and sets no CORS headers (ADR-0027, ADR-0029, ADR-0030).
  • Relationship api-reads-writes-db: Calendar API → Calendar database (PostgreSQL 18): Database connections are TLS-only: the Flexible Server sets require_secure_transport=on and the connection string verifies the server certificate and hostname (ADR-0014, ADR-0031).
