# Repo tooling

Every script in this repo is a .NET 10 *file-based app* (`dotnet run x.cs`, no project file), kept in `tools/<name>/` or in the skill folder it belongs to, with that folder's own analyzers, `.editorconfig` and xUnit tests ([ADR-0017](../docs/decisions/0017-dotnet-file-based-apps-for-repo-tooling.md)). The only exception is `tools/doctor/doctor.sh`, a bootstrap check that must run without the SDK. Don't write new tooling in Python, Node or shell. Read this page before writing or fixing a tool.

## Layout and discovery

- A tool is `tools/<name>/<name>.cs` (the entry point, with a `#!/usr/bin/env -S dotnet run` line and a usage comment), one or more `#:include`d implementation files, and `tests/<name>.tests.cs`. Copy `tools/tool-versions/` as the pattern, including `tests/Directory.Build.props`.
- `just tools test` runs every `*.tests.cs` under the `tool_dirs` list in `tools/mod.just` and `dotnet format whitespace --verify-no-changes` on each directory. `tools` is in the list, so a new `tools/<name>/` is checked automatically. A tool inside a skill folder must be added to `tool_dirs` by hand, or neither its tests nor CI validate it (the gap behind #190 and #209). After adding one, check that `just tools test` prints its test file.
- Package pins (`#:package` directives and `Directory.Build.props`) must match `backend/Directory.Packages.props`; `just tools versions` fails on drift and `just tools versions --fix` rewrites them. The first run of a tool writes `packages.lock.json` next to it: commit it. CI restores in locked mode.

## SDK and build gotchas

- The repo-root `global.json` pins the SDK the tools run on, and `backend/global.json` pins the same one; `just tools versions` fails when the two `sdk` blocks differ, and `just doctor` fails when no installed SDK satisfies the root file. The pin matters because file-based apps default to `PublishAot=true`, so every tool lock file records `Microsoft.DotNet.ILCompiler` and `Microsoft.NET.ILLink.Tasks` at the SDK's own runtime version, and CI's locked restore fails with `NU1004` on any other SDK (#645). Every CI job that runs a tool installs the SDK from `global.json`.
- **Bumping the SDK** (Dependabot's `dotnet-sdk` update, or by hand): set the same `sdk` block in both `global.json` files, install that SDK, run every tool and test app once outside CI so restore rewrites its lock file (`just tools test`, plus `dotnet build <tool>.cs` for each tool entry point that has a `packages.lock.json` beside it), check that the lock diff changes only those AOT packages, and commit the lock files on the same branch.
- `#:include` needs .NET SDK **10.0.300 or later**, which the pin satisfies. On 10.0.1xx or 10.0.2xx every tool that uses it fails with `Unrecognized directive 'include'` before compiling. A skill folder copied into another repo still needs only 10.0.300.
- File-based apps default to `PublishAot=true`, so reflection-based `System.Text.Json` fails analysis. Use `JsonDocument`, `Utf8JsonWriter` or a source-generated `JsonSerializerContext` (see `tools/seed-dev/SeedPlan.cs`).
- Warnings are errors, with the same analyzers as the backend. The traps that bite most: S103 (lines over 140 characters, which nothing fixes automatically), IDE0007/IDE0008 (`var` only when the type is apparent on the right-hand side), IDE0305 (use collection expressions instead of `.ToList()` into a typed variable), CA1307 (pass a `StringComparison`), S127 (don't change a `for` loop variable in its body), S4036 (start processes by absolute path), S6966 (await the async console methods). The first `dotnet run` compiles the file and takes a few seconds; later runs are cached.

## Formatting a tool

`dotnet format` doesn't accept file-based apps. To apply code fixes, convert the tool into a scratch project inside its own directory, so its `Directory.Build.props`, `.editorconfig` and `SonarLint.xml` still apply, format that, copy the code back and keep the `#!`/`#:` header lines:

```bash
cd tools/<name> && mkdir -p .scratch && cp *.cs .scratch/ && cd .scratch && dotnet project convert <name>.cs
```

Then `dotnet format` inside `.scratch`, copy the formatted bodies back and delete `.scratch`. The whitespace check that CI runs (`dotnet format whitespace --folder --verify-no-changes <dir>`) does accept file-based apps, so run it last.

## Reporting what a tool's checks covered

A scratch build that drops the folder's `Directory.Build.props`, `.editorconfig`, `SonarLint.xml` or package settings can pass locally and fail the CI analyzers (#185). When you report verification, name the directory, the command, and whether `just tools test` discovered the tests.

## ci-timings

`tools/ci-timings/` samples how long a workflow's jobs and steps take from the runs GitHub keeps (`just tools ci-timings --job Frontend`, needs `gh auth status` to pass). Only completed, successful runs count; `--branch <name>` keeps only the runs of one branch, which is how a PR measures itself against `main`. It prints Markdown tables for a benchmark record (`docs/benchmarks/README.md`): one row per job with min, median, p90 and max, and, for each `--job`, one row per step. `--superseded` reports on cancelled runs instead. It pairs each cancelled pull request run with the next run of its branch. It then times how long that run waited for its first job and for all of them, when the old run's runners heard of the cancel (bounded by the steps they still started and the first step that ended cancelled), and when the old run ended. Control rows cover pull request runs that superseded nothing (record 0008). `--created "<2026-11-06T16:15:00Z"` passes a date range to `gh run list`, so a record's before window can be reproduced after newer runs have joined the list. `CiTimings.cs` holds the parsing, the pairing, the nearest-rank statistics and the rendering, which the tests cover; the entry file only calls `gh`.

`--baseline --created <range>` writes the pinned run-time baseline of [ADR-0045](../docs/decisions/0045-run-time-regression-gates-for-ci-jobs.md) to `.github/ci-baseline.json` (`--out`): from the successful push and `workflow_dispatch` runs on `main` in the range, per path (`publication` when the Docs site step "Build and verify publication artifact" succeeded, otherwise `check`) and gated job, it stores n, the window, commits and run IDs, the median, the MAD of log seconds, p90, p95, the maximum and the threshold `ceil(max(exp(m + z·1.4826·MAD), median + max(floor, r·median)))`, with `z = Φ⁻¹(1 − α/J)` and J the number of jobs the baseline holds. A path whose jobs have fewer than `--min-runs` (30) runs is marked `provisional`. `--holdout <range>` back-tests the thresholds on the runs in that range, on `main` and on pull requests separately, with the observed false-failure rate per job and per run and its one-sided 95 % Clopper–Pearson upper bound. `--alpha`, `--floor` and `--margin` override the constants. `Baseline.cs` holds the statistics, the path rule, the file format and the back-test, which `tests/BaselineTests.cs` covers. The gate itself is `.github/ci-gate.jq`, run by `CI result`; `tests/GateTests.cs` runs that file with `jq` (which must be on PATH: the tests fail without it) and checks that `ci.yml` runs it.

`--trend [--issue]` is the trend check on `main` of ADR-0045, run daily by `.github/workflows/ci-trend.yml`: it takes the last 20 successful push runs on `main` created after the baseline's last run, compares each job with its baseline sample (the file keeps each job's durations) by an exact one-sided Mann–Whitney test conditional on ties, at p < 0.002, and reports a job as slower only when the Hodges–Lehmann shift is also at least max(10 s, 5 % of the baseline median); a job that is faster by the same rule is listed as a suggestion to re-pin. With fewer than 20 runs since the baseline it concludes nothing. `--issue` comments on the open `performance` issue titled "CI run-time trend: jobs slower than the pinned baseline on main", or opens it, and only when a job is slower. `Trend.cs` holds the test, the estimate, the verdict, the report and the issue decision, which `tests/TrendTests.cs` covers on constructed histories.

## handover-watch

`tools/handover-watch/` is the watch of the `issue-handover` skill: `just tools handover-watch <issue>` prints what is new on an issue and its delivery PRs since the last run and records it, so a handover tick is one call (needs `gh auth status` to pass). A delivery PR is a PR of this repository that cross-references the issue with `Closes`, `Fixes`, `Resolves` or `Refs` before its number in the body and was opened by the owner, a member or a collaborator, whether open, closed or merged. A bare mention in prose does not count, nor does a PR from someone without write access (anyone can write `Refs #N`) or from another repository, where `#N` is another issue; `--pr N` adds a PR either rule leaves out. It covers the issue's comments, each PR's conversation comments, inline review comments and submitted reviews, and each PR's state when first seen and on every change. An empty `COMMENTED` review (the wrapper GitHub puts around inline comments) and a pending review are left out; an approval with an empty body is kept.

The first line names the watched PRs with their state and says how many items are new, or `nothing new`. Each item is a header line (`=== kind:id · #N` or `PR #N` `· author · association · agent-footer: yes|no · …`), its link, and its body indented by two spaces, so no body line can pass for a header. The association is the author's relation to the repository as GitHub gives it (`OWNER`, `MEMBER`, `COLLABORATOR`, `CONTRIBUTOR`, `NONE`, …). An item a maintainer has hidden (minimized) for any reason, from `spam` to `outdated`, carries `hidden: <reason>` after the association and prints only its header and link, so a hidden prompt injection never reaches the agent's context (#378); control characters such as terminal escapes and bidirectional overrides are replaced, and a header is always one line, whatever a file path or login holds. `agent-footer: yes` means the last non-blank line starts with `🤖 Generated with` and is not quoted, a heuristic rather than authentication. What was printed is appended to `.plan/handover-watch/<issue>.seen` (git-ignored, one `kind:id` per line, in the checkout that holds the tool, so two worktrees watching one issue do not consume each other's items), after printing, so a failed run prints again rather than loses an item. `--peek` prints without recording; deleting the file starts over. Edits to an item already printed, a hide after the item was printed, and CI check results are not reported. A tick is `gh api graphql` (#363): the first query asks for the issue's comments, its cross-references with only the fields that decide whether a PR is a delivery PR, and each `--pr` PR in full, so a stranger's PR costs its header and never its comments. The next query asks, in one call, for the delivery PRs' comments, reviews and review threads, and for the next page by node ID of any list longer than its page (100 items, 10 review threads, 50 comments per thread). An issue with no delivery PR takes one call and one with delivery PRs two; record 0013 measured 2.3–2.4 s instead of 2.8–4.5 s for 3 to 9 PRs, with the same output. After 20 follow-up rounds the run stops following, prints and records what it read, names the lists it left unread on stderr and exits 1, so a flood of items cannot silence the watch. IDs come from `fullDatabaseId` (the REST IDs, so the seen keys are stable), and a bot's login gets back the `[bot]` suffix GraphQL leaves out. `HandoverWatch.cs` holds the argument parsing, the queries, the response parsing with the PR filter, the seen-ID logic and the rendering, which the tests cover against canned responses; the entry file only runs `gh`.

## delivery-dashboard

`tools/delivery-dashboard/` is the snapshot tool of the delivery dashboard (story 0053, [ADR-0049](../docs/decisions/0049-build-the-delivery-dashboard-from-daily-snapshots-on-the-docs-site.md), epic #595, slice #596). `just tools delivery-dashboard snapshot [--repo OWNER/NAME] [--workflow ci.yml] [--runs 30] [--date YYYY-MM-DD] [--out FILE]` samples the newest successful push runs of the workflow on `main` (needs `gh auth status` to pass), reuses `ci-timings` for the parsing and the path rule (`CiTimings.cs`, `Baseline.cs`, included from `tools/ci-timings/`), and writes one JSON snapshot: version 1, the date, the repository, and a `ci` section with the runs sampled, their window and, per job and path (`check` or `publication`), the count, min, median, p90 and max of the execution time in seconds, all marked `measured`. `just tools delivery-dashboard check FILE...` validates snapshot files and exits 1 on a problem. The snapshot is written only when it passes the same rules, so a failing run writes nothing.

The rules (`SnapshotRules.cs`) are the public-safety rule of the story, because the repository is public: every field must be in the schema (an unknown or missing field fails and is named by its JSON path), and no string or field name may look like a machine path (`/home/…`, `/tmp/…`, `C:\…`), a session or task handle, a UUID or an e-mail address. A new section adds its fields to the schema and its keys to the tests; it never relaxes the privacy patterns. The tests (`tests/delivery-dashboard.tests.cs`) cover the aggregation on constructed runs, each rule with a case that must fail, and a snapshot the tool wrote must pass. They are proved the other way too: with the path and e-mail checks disabled, the tests that name them fail.

The `quality` section (slice #599; `QualitySection.cs` and `QualityRules.cs`, optional so that snapshots written before it still validate; `--quality-runs 100` sets its sample) classifies the newest completed runs of the workflow into `main` (pushes to `main`) and `pullRequest` scopes. It reads the Actions REST API because that reports `run_attempt`, which `gh run list` does not. The classes are `passed`, `passedAfterRerun` (a later attempt succeeded, so a failure was hidden), `failed` (failure, timed out or startup failure), `superseded` (cancelled while a later `pull_request` run of the same branch existed, found with `Supersession.Pair`, so marked `inferred`), `cancelled` and `other`. A cancelled or superseded run is no failure, and its jobs are trials in no rate (`CI result` fails there only because the others were cancelled). A job's failure rate counts the attempts of every run (`filter=all`, so a failed first attempt that a rerun turned green counts) that ended in success or failure, with a two-sided 95 % Clopper-Pearson interval built on `Probability.UpperBound`. Under 20 trials a row is `inconclusive` and carries its counts but no rate and no interval. The jobs responses the CI section fetched are reused for runs never re-run (#614), so the same run is not fetched twice. A pull request from a fork can bring its own `ci.yml`, so in the `pullRequest` scope only job names that runs on `main` also have are kept (#613); otherwise a name could fail the privacy rules or pose as `CI result`. Each scope holds an Actions search query and the ids of its newest 50 failed and rerun runs, so the page links every count to public runs. The guard numbers are the attempts of the Tooling job's step "Test and lint tooling" per day, marked `inferred` because that step also runs the other tool tests. Tests: `tests/QualityTests.cs`, included by the tests app.

The `agents` section (slice #600; `AgentSection.cs`, `AgentRules.cs`, optional like `quality`) holds proxies for agent-driven delivery from GitHub only, read with one GraphQL query for the 100 most recently updated issues (older issues are not covered), their first 100 comments and the pull requests of the same repository that mention them. It is **not** token or money cost, and the page says so. Per issue number (never a login, title or comment text) it keeps: valid count comments, malformed ones, tasks and subagents started, comments, reviews on the mentioning pull requests, and the pull requests. A count comment is the line of the `issue-handover` skill, `Tasks started: N. Subagents started: M.`, anywhere in a comment (case-insensitive, one half alone is enough, quoted lines starting with `>` are ignored). A comment that names a count without a whole number of at most 1000 is malformed: it is counted and contributes nothing, and never fails the run. An issue without a valid count comment is listed with `tasks` and `subagents` null (no cost data), as long as it has a comment or a mentioning pull request. Comment, review and pull request counts are **measured**; tasks and subagents are what an agent wrote, so **inferred**. The rules check that each total equals the sum of the listed issues. Tests: `tests/AgentTests.cs`.

`.github/workflows/dashboard-snapshot.yml` runs it daily at 06:47 UTC and on `workflow_dispatch`, outside `CI result` ([ADR-0046](../docs/decisions/0046-run-ci-jobs-only-for-the-paths-they-check.md)). The `snapshot` job has read access only: it takes the snapshot, checks the file again and uploads it as an artifact. The `publish` job has `contents: write` and runs git commands only: it commits the file as `snapshots/YYYY-MM-DD.json` to the never-merged `dashboard-data` branch (an orphan branch with a README, created on the first run), skips the commit when the day's file is unchanged, and retries the push up to three times after a rebase. A second run on the same day replaces that day's file. Size and retention limits for the branch come with slice #601.

## delivery-guards

`tools/delivery-guards/` holds the mechanism guards of epic #380 (#387): deterministic checks over `.github/workflows/ci.yml`, `backend/mod.just`, `tools/mod.just` and the backend MSBuild files, each failing when the mechanism of a delivery performance fix is reverted. They never measure time; the run-time gate of ADR-0045 says that a job got slower, a guard says why. Each guard (`DeliveryGuards.cs`) has an id, the issue it protects and its benchmark record: `superseded-runs` (#348, record 0008), `format-whitespace-only` (#350, 0010), `parallel-tool-tests` (#351, 0011), `ci-result-needs-all` (#368), `single-web-typecheck` (#276, 0006), `docs-site-job` (#274, 0004) and `changes-job` (#418, 0016). `ci-result-needs-all` is generic: `CI result` must need every other job except `Cancel superseded runs`, so a new job fails it until it is added to `needs`; it accepts a skipped job only in the two exact forms that check the Changes job's output (ADR-0046). `changes-job` requires the Changes job to run on every event and to run `.github/ci-changes.jq`, and every other job but `CI result` and `Cancel superseded runs` to need it with `if: needs.changes.outputs.<id> == 'true'`; a new job fails it until it has a rule and an output. The same test app runs `.github/ci-changes.jq` with `jq` on canned file lists (`ChangesRulesTests`): each path set, a file in several sets, an unmatched file, a rules change, a truncated listing, a push and a dispatch; jq missing fails the tests rather than skipping them. The test app runs every guard against the checkout (one test per guard, so a failure names it) and each guard against a small fixture broken in every way it catches; `just tools test` runs it in `just check` and in the Tooling job. `dotnet run tools/delivery-guards/delivery-guards.cs` prints the same report by hand. `WorkflowYaml.cs` reads the workflow with YamlDotNet's representation model (no reflection-based serializer) into the few node types the guards query; YamlDotNet is pinned in `backend/Directory.Packages.props`, which no backend project references for it, so Dependabot updates it and `just tools versions` keeps the `#:package` pins in step. A workflow that is not valid YAML fails every guard. `superseded-runs` also keeps what makes the cancel job's `actions: write` safe: it must run only for same-repository pull requests, hold no other permission and fetch no code (`actions/checkout`, `git clone` or `fetch`, `gh pr checkout`). A guard that stops matching after an intended workflow change is updated in the same PR, with the reason in its message. Guards about test code live in that code's suite: `ApiTestParallelismTests` (#349, record 0009), the docs loader's listing count in `docs-loader.test.ts` (#273, record 0003) and `apps/web/dev/vitestConfig.test.ts` (#275, record 0005).

## agent-hooks

`tools/agent-hooks/` is the set of Claude Code hooks wired in `.claude/settings.json` ([ADR-0042](../docs/decisions/0042-layered-agent-guidance-and-hooks.md)): it denies discarding unstaged work, public posts with private details, edits of generated files and a `git push` to a branch whose PR is merged or closed; asks before the shared database is touched from a linked worktree; and reports over-long C# lines, a stale API contract and a PR to `main` that names no issue it closes or refers to. The code is one file per guard or check (`BashGuard.cs`, `EditGuard.cs`, `LineLengthCheck.cs`, `ContractCheck.cs`, `PullRequestLinkCheck.cs`), plus `ShellCommand.cs` (command splitting that keeps quoted, `$(...)` and heredoc text whole, #355, and unwraps `NAME=value` prefixes and wrappers such as `env`, `command`, `sudo` and `timeout`, so each guard sees the command that runs, #376; `bash -c`, `eval` and `xargs` are not unwrapped), `PullRequestLookup.cs` (asks `gh pr view` for a PR's state, or its base and body), `ExternalCommand.cs` (runs a process with a time limit), `HookRunner.cs` (subcommand dispatch), `GitProbe.cs` behind `IRepoProbe.cs` (questions asked of git) and `HookProtocol.cs` (the hook JSON in and out); each tested class has a matching `tests/<Class>Tests.cs`, included by the one test app `tests/agent-hooks.tests.cs`. Each subcommand reads the hook JSON on stdin, so you can try one by hand:

```bash
printf '{"tool_name":"Bash","tool_input":{"command":"git restore AGENTS.md"},"cwd":"%s"}' "$PWD" | dotnet run tools/agent-hooks/agent-hooks.cs -- pre-bash
```

The public-post guard covers `gh issue` and `gh pr` `create`, `comment`, `edit` and `review`, and any `gh api` call with a field or `--input`. It scans the command's words, and in place of a body source's local path, what the source holds. The sources are the file of `--body-file`, `gh api --input` and a typed field's `@` value (`-F body=@file`); for `-`, it reads the command's heredoc. A raw field (`-f body=@x`) is sent as written, so it is scanned as written. So is a word starting with `-` after one of these options, because an earlier option may have taken the option as its value. The hook sees the command before it runs, so it reads a source through what the command itself states (#374): it expands `~`, `$NAME` and `${NAME}` from earlier assignments in the command (`S=…`, `export S=…`), then from its own environment; it reads a file that an earlier `cat` or `tee` heredoc, or `echo` or `printf`, writes (`>`, `>>`); and for `-` it reads a `< file` redirect, the files of a `cat` piped in, or the words of any other command piped in (`jq -n '{body: …}' | gh api … --input -`). That model can differ from what the shell does, so whatever it contributes is scanned together with the words that name the source and the file as it is on disk, never in their place. Only a literal file read from disk, or a heredoc, replaces the words. A write whose text holds a `$` or a backtick (which the shell may expand), or any other command's output redirected to a file, is not modelled. When it still cannot read a source, such as a variable the agent's shell set in an earlier call or a `$(...)` path, it scans the words that name it instead, so only a path that itself looks private is caught. A file reads as text only when it is a regular file of at most 1 MiB with no NUL byte. An empty file, a pipe, a device, a larger file or a binary one reads as empty, so an upload sent with `gh api --input` is neither read whole nor denied on its bytes; the line-length check reads files the same way (#355, #369, #374).

The stale-contract check at stop counts a file as changed only while it still differs from `origin/main`, so a squash-merged branch stops tripping it. It passes when `contracts/openapi.json` was written after every changed contract source (any API build regenerates it, so an unchanged contract no longer blocks every turn), and the same holds for `schema.gen.ts` against the contract; a deleted source still blocks (#254).

The push guard runs `gh pr view <branch> --json number,state` (10 s limit) only for a `git push`. It checks the destination branch of each refspec: the current branch for a bare push or `HEAD`, or the one an earlier `git switch -c` or `git checkout -b` in the same command created, so the remedy it names passes. A merged or closed PR denies; it lets the push through whenever gh has no answer (no PR, no gh, not signed in, offline, timed out) and for a detached HEAD, a delete, a dry run, `--all`, `--mirror` or tags only (#293).

The PR link check is an inform hook and Claude Code only ([ADR-0044](../docs/decisions/0044-claude-first-agent-automation.md)); the `Closes` rule in `AGENTS.md` is what other agents follow. On `gh pr create` and on `gh pr edit` with a new body, it adds a note, never a decision, when the PR targets `main` and the body (`--body`, the file of `--body-file`, or the heredoc of `--body-file -`) has neither a closing keyword (`Closes`, `Fixes`, `Resolves`) nor `Refs` before an issue. On a retarget (`gh pr edit --base main`) it notes a body without a closing keyword, even with `Refs`, because a stacked PR gets its `Closes` then. A create without `--base` targets `origin/HEAD` (`main` when git cannot tell). An edit asks `gh pr view [<pr>] --json number,baseRefName,body` (3 s limit; it took 0.7–0.9 s when measured) for the base or the body it leaves as they are. When the body cannot be known (`--fill`, `--template`, `--web`, an unreadable file) or gh has no answer, there is no note (#321).

Exit 0 with JSON is a decision or a note; exit 2 with stderr is a usage error; any other failure (for example an SDK below 10.0.300) is non-blocking for Claude Code, and the rules in `AGENTS.md` still apply by hand. Each handler carries an `if` filter (`Bash(git *)`, `Edit(**/*.cs)`, …) so unrelated commands and edits start no process. Personal overrides go in the git-ignored `.claude/settings.local.json`. Revisit the hooks when their latency is still felt in sessions, when Claude Code documents native nested `AGENTS.md` loading (drop the `CLAUDE.md` shims), or when a rule in `AGENTS.md` is ignored repeatedly (promote it to a hook). During the Claude-first period of [ADR-0044](../docs/decisions/0044-claude-first-agent-automation.md), new ask and inform hooks and other automation may be Claude Code only; the period is revisited when the maintainer states it, and ending it is a new ADR.
