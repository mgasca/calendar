0044 · Edit a task from the Today view

Status: implemented · Date: 2026-11-07 · Issue #467 · PR #485 · PR #495 · PR #499

ADRs: ADR-0014 · ADR-0015 · ADR-0018 · ADR-0020 · ADR-0021 · ADR-0041 · ADR-0043 · ADR-0047

Story

As a calendar editor, I need to open a task from the Today view to change its title, due date, priority or notes, so that I can correct or reschedule it.

Tracked in issue #467, part of the Today view epic #458.

Background

Tasks can be added (0003, in a dialog since 0006), completed, reopened and deleted (0007), but not edited. The API has GET, POST and DELETE on /api/tasks, complete, reopen and bulk, and no update. The only way to fix a typo or move a single task to another day is to delete it and add it again; triage (0007) can reschedule overdue tasks in bulk, but nothing edits the title, priority or notes.

On the Today view, a task’s title is part of its checkbox label, so selecting the title toggles completion. This story makes the title open the task for editing instead, and keeps the checkbox for completing.

It follows event editing (#466, card 0043) and uses the same version check for changes made elsewhere. Both regenerate the API contract, so they are delivered one after the other.

Agreed scope

  • Opening a task: on the day page (/ and /day/:date), the title of every task under Overdue and Due today (or Due this day) is a button. Selecting it, with the mouse or the keyboard, opens the task dialog titled Edit task, prefilled with the stored title, deadline (none, a date, or a date and time), priority and notes. The dialog loads the task first and says so while it loads; if the task no longer exists, it says that and the day refreshes.
  • Checkbox unchanged: the checkbox still completes and reopens the task, with the same name for screen readers (the task’s title). Opening the task for editing never toggles it.
  • Editing: title, deadline, priority and notes can be changed, with the validation and daylight-saving handling of Add task (0003, ADR-0043). Save task saves; Cancel and Escape close without saving and without a prompt, except while saving. Completion is not part of the form: editing an open task keeps it open, and editing a completed one keeps it completed.
  • After saving: the dialog closes, the day and week agendas and the My tasks lists refresh, and a status message says “Task saved.” A task moved to another day leaves the day’s list. Focus returns to the task’s title button, or to the day heading when the task has left the day.
  • Changed elsewhere: the dialog saves against the version it loaded. If the task was changed in the meantime, including completed or reopened in another tab, the save is refused, the dialog says “This task was changed elsewhere. The latest version is shown; check it and save again.”, and the form reloads with the latest values. If it was deleted in the meantime, the dialog says so and the day refreshes.
  • Failures: a network or server error keeps the dialog open with what was typed and a message, and saving can be retried.
  • Ownership: another user’s task cannot be read or changed; the API answers as if it did not exist (ADR-0041).

Not in this story

  • Editing from My tasks, triage or the week view. The endpoint and dialog are reusable; the entry points are follow-up issues.
  • Deleting from the dialog. Each row already has Delete (0007).
  • Completing or reopening from the dialog; the checkbox does that.
  • Events. That is #466, card 0043.
  • Merging the user’s edits with changes made elsewhere. On a conflict the latest version replaces the form.
  • A “Discard changes?” prompt on closing an edited dialog.
  • The fading save notification of #463. If it has merged when this story’s UI lands, the status message uses it; otherwise it uses the plain status message of Add task.

Dependencies

  • Builds on 0003, 0006 and 0007.
  • Follows event editing (#466, card 0043): both regenerate contracts/openapi.json and the TypeScript client, and this story reuses its version handling.
  • The task row is also changed by #460 (delete errors) and #462 (phone layout); this story’s row change comes after them.

Acceptance criteria

  1. Given a task due today on the Today view, when I select its title, change the due date to tomorrow and save, then the dialog closes, “Task saved.” is announced, the task leaves today’s list, and it is listed on tomorrow’s. Move to tomorrow from the day (moves a task to tomorrow: it leaves the day, the save is confirmed, focus goes to the heading); API, both days’ agendas (UpdateTask_ReplacesTheEditableFields_AndReturnsANewVersion).
  2. Given the edit dialog is open, when I change the title, priority or notes and save, then the row shows the new title, priority or notes indicator. Title and priority in the row (shows a new title and priority in the row and returns focus to the title); request (opens prefilled and saves a new due date with its version). The notes indicator follows the same refetch and is not asserted separately.
  3. Given a task with a due time, when I open it, then the deadline shows Exact date and time with its local date and time; changing it to No deadline and saving removes it from the day. Timed prefill and clearing the deadline (opens a timed task with its local time, and clears the deadline); fromTask (shows each deadline kind); API (UpdateTask_SwitchesBetweenDeadlineKinds_AndClearsTheDeadline). Leaving the day after clearing follows from the agenda refetch, as in criterion 1.
  4. Given the edit dialog is open, when I clear the title and save, then nothing is sent and the field says what to fix, as in Add task. Blank title (validates like Add task and sends nothing); API 400 (UpdateTask_Invalid_Returns400WithTheField_AndLeavesTheTaskUnchanged).
  5. Given I opened a task and it was then changed elsewhere, when I save, then the dialog stays open, says the task was changed elsewhere, and shows the latest values; saving again succeeds. Conflict reload (reloads the latest version when the task was changed elsewhere, then saves).
  6. Given I opened a task and it was then deleted elsewhere, when I save, then the dialog says the task no longer exists and the day no longer lists it. Day view (says so when the task was deleted elsewhere, and the day drops it); dialog (says so when the task was deleted elsewhere and stops saving); opening (says when the task can no longer be opened).
  7. Given a save fails with a network or server error (not 400, 404 or 409), when it fails, then the dialog stays open with my values and a message, and saving again succeeds. Server error and retry (keeps the values after a server error and saves on retry).
  8. Given a task row, when I select its title, then the edit dialog opens and the checkbox is not toggled; when I select the checkbox, then the task is completed as before, and the checkbox is still named by the task’s title. Title opens without toggling; checkbox completes by its name (opens from the title without toggling, and the checkbox still completes the task by its title).
  9. Given the Today view, when I use the keyboard alone, then each task title is a button I can reach with Tab and open with Enter or Space, and focus returns to it after Cancel or a save that keeps the task on the day. Keyboard (opens from the keyboard); after Cancel (opens from the title without toggling, and the checkbox still completes the task by its title); after a save (shows a new title and priority in the row and returns focus to the title).
  10. Given two users, when one requests or updates the other’s task by id, then the API answers 404 and the task is unchanged (API tests). Read (AnotherUsersTask_IsNotFoundForReadCompleteReopenAndDelete_AndStaysUnchanged); update (AnotherUsersTask_IsNotFoundForUpdate_AndStaysUnchanged).
  11. Given an update that sends a stale version, when the API handles it, then it answers 409 and the stored task is unchanged (API tests). Stale version after a complete elsewhere (UpdateTask_AfterACompleteElsewhere_Returns409_AndLeavesTheTaskUnchanged), which fails without the version check (negative control in PR #495).
  12. Given the Light and Dark themes at desktop and phone widths, when I open and save a task, then the row and dialog are legible and usable in both (checked in the running app, with screenshots in the UI PR). Checked by hand in the running app; screenshots in PR #499.
  13. Given the change is complete, when I run just check, then it passes, including the regenerated contract. just check on the delivering revision of PR #499, and CI on each PR.

No new ADR is expected.

Other decisions (not ADR-worthy)

  • A version sent back on update: the task response carries the same opaque version as events (#466, card 0043), and the update must send it. Complete and reopen only detect a race inside one request; an edit dialog stays open for a while, so it needs to detect a change made after it opened.
  • Full replacement of the editable fields: the update takes title, priority, notes and the deadline, with the create rules. Completion is left alone, so an edit never completes or reopens a task by accident.
  • Completed tasks can be edited (proposed in PR 0, #485, which merged without changes): the Today view lists completed tasks under Due today, and correcting a title or notes of a done task is harmless. Rescheduling a completed task is allowed too; it stays completed.
  • The title is the button, the checkbox keeps its name: the title moves out of the checkbox’s <label> into a <button> styled as text, and the checkbox is named by that title, so assistive technology still announces “Buy milk, checkbox”.
  • The dialog loads the task: the agenda carries only hasNotes and no version, so opening a task fetches it by id.

API

  • PUT /api/tasks/{id} (UpdateTask): body title, priority (default medium), notes, dueDate or dueAt (neither clears the deadline), and the required version. 200 with the updated task and its new version; 400 with field errors (create’s keys; a missing version is a binding 400); 404 when the task does not exist or belongs to another user; 409 when version is stale, with nothing written. A complete or reopen changes the version, so it makes an open edit stale.
  • Every task response (GET, list, POST, complete, reopen, PUT) carries version. Like events, the generated TypeScript type is number | string; the client sends back what it got.

Testing

  • Domain: TodoTaskTests (Update_ReplacesTheEditableFields_AndKeepsIdOwnerAndCompletion, Update_CanClearTheDeadline_AndKeepsAnOpenTaskOpen, Update_WithInvalidValues_Throws_AndChangesNothing).
  • API with Testcontainers: TaskEndpointsTests (fields and agenda move, deadline kinds, completed stays completed, stale version, invalid, unknown, version agreement across list, get and actions) and OwnershipTests.
  • Vitest with MSW: EditTask.test.tsx for the dialog against a task store with the API’s version check, and EditTaskFromDay.test.tsx for the routed day view (move, row update, title versus checkbox, deleted elsewhere, keyboard).
  • The running app (throwaway stack, Light and Dark, 1280×900 and 390×844): open a timed task, change title and priority, save; move a date-only task to tomorrow.

Lessons learned, known issues and follow-ups

  • Stacking on the event UI. Both stories add title buttons, dialog state and focus handling to DayView.tsx and the .item-open style, so the task UI was stacked on the event UI branch; the merge combined the two focus helpers into one (focusTitleOrHeading).
  • A replaced dialog element. The loading dialog and the form’s dialog are different elements, so a test that holds the first one and waits for the form inside it never finds it; the tests wait for the form’s Title field and then take the dialog.
  • Week view and My tasks: opening a task from them is not in this story; the row keeps the old label there. Follow-up: #500.
  • Completed tasks can be edited and stay completed, as proposed in PR 0.

User guide

Changing a task

  1. On the day page, select the task’s title. The Edit task form opens with the task’s details. (The checkbox beside it still marks the task done.)
  2. Change the title, the deadline, the priority or the notes, then select Save task. The form closes, a message says Task saved., and the day shows the change. A task moved to another day leaves this day’s list.

If the task was changed somewhere else since you opened it, including being ticked off in another tab, the form tells you and shows the latest version: check it, make your change again and save. If it was deleted, the form says it no longer exists.

Tasks can be changed from the day page for now, not from the week or My tasks.
