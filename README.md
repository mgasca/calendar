# Calendar

Monorepo for the Calendar application: a .NET backend and a web front end, with room for more UIs.

## Layout

```
backend/                 .NET 10 solution (Calendar.slnx)
  src/Calendar.Domain/     Domain model; no framework dependencies
  src/Calendar.Infrastructure/  EF Core DbContext, mappings, migrations (PostgreSQL)
  src/Calendar.Api/        ASP.NET Core minimal API
  tests/                   xUnit v3 test projects (one per src project) + Calendar.Testing (Testcontainers support)
compose.yaml             Local backing services (PostgreSQL); init scripts in docker/postgres/init/
contracts/openapi.json   API contract, generated by the backend build — commit changes
frontend/                pnpm workspace
  apps/web/                React + Vite + TypeScript web UI
  apps/docs/               Astro + Starlight ADR log and reader
  packages/api-client/     Typed client generated from contracts/openapi.json, shared by all TS UIs
docs/decisions/          Architecture Decision Records (MADR)
docs/stories/            User stories: background, decisions, implementation notes, user guide
.github/                 CI and Dependabot
```

New UIs go under `frontend/apps/` (TypeScript) or a new top-level directory for other stacks; they should consume `contracts/openapi.json`.

## Prerequisites

| Tool | Version source | Notes |
| --- | --- | --- |
| .NET SDK | `backend/global.json` | 10.0.100 or later feature band |
| Node | `frontend/.node-version` | 24; use a version manager, since Ubuntu's apt `nodejs` is too old and lacks Corepack |
| pnpm | `packageManager` in `frontend/package.json` | Provided by Corepack (bundled with Node 24); don't install it globally |
| Docker | n/a | Engine running and reachable; needed for the local database and for integration tests (Testcontainers) |
| GNU Make | n/a | Optional; it only wraps the native commands |

Run `make doctor` (also run by `make setup`) to check all of these.

### One-time setup on Linux / WSL

```sh
# .NET SDK, user-local (no sudo)
curl -sSL https://dot.net/v1/dotnet-install.sh -o /tmp/dotnet-install.sh
bash /tmp/dotnet-install.sh --channel 10.0 --install-dir "$HOME/.dotnet"
echo 'export DOTNET_ROOT=$HOME/.dotnet PATH=$HOME/.dotnet:$HOME/.dotnet/tools:$PATH' >> ~/.bashrc

# Node via fnm, which reads .node-version and switches automatically on cd
curl -fsSL https://fnm.vercel.app/install | bash -s -- --skip-shell
echo 'eval "$(fnm env --use-on-cd --version-file-strategy=recursive --corepack-enabled --shell bash)"' >> ~/.bashrc
exec bash                      # reload the shell
cd calendar/frontend && fnm install && corepack enable pnpm

make doctor                    # everything should be ✓
```

## ADR website

The Astro + Starlight site renders the canonical Markdown in `docs/decisions/`. Its ADR log provides navigation to individual records and displays their status. Every ADR merged to `main` is published, including proposed and superseded decisions. Edit the Markdown sources and the log there; generated pages are build output and are not committed.

After installing the frontend dependencies with `pnpm --dir frontend install --frozen-lockfile`, use `make dev-docs` to develop the site. `make build-docs` builds and verifies the static output in `frontend/apps/docs/dist`; `make preview-docs` serves that output. These tasks require Node and pnpm, but do not require the backend or database.

To reproduce the GitHub Pages project path locally:

```sh
DOCS_SITE_URL=https://mgasca.github.io/calendar/ make build-docs
DOCS_SITE_URL=https://mgasca.github.io/calendar/ make preview-docs
# Open http://localhost:4321/calendar/
```

`DOCS_SITE_URL` is the full public URL, including any project path. The site derives its origin and base path from this URL, so custom domains and root-hosted sites work without hard-coded `/calendar/` links. Local development defaults to the site root.

GitHub Pages uses **Settings → Pages → Build and deployment → Source: GitHub Actions**. The CI workflow builds and checks the site for pull requests, merge queues, and manual runs. Only a push to `main` uploads the Pages artifact and deploys it, after the backend, frontend, and tooling checks succeed. The deployed artifact is the same output verified in that run. The workflow reads the public URL from GitHub Pages configuration and publishes through the `github-pages` environment; restrict that environment to `main` if configuring deployment protection rules.

The configured publication URL is [mgasca.github.io/calendar](https://mgasca.github.io/calendar/). The site becomes available after the workflow's first successful deployment from `main`; an unmerged branch or pull request does not update it.

| Service | Dev / test provisioning | Production | ADR |
| --- | --- | --- | --- |
| PostgreSQL 18 | Docker Compose (localhost only) / Testcontainers | Managed PostgreSQL (fallback: SQLite on a persistent volume with Litestream) | [0014](docs/decisions/0014-postgresql-database-engine.md), [0016](docs/decisions/0016-local-database-provisioning.md) |

### Local database

```sh
make db-up        # starts PostgreSQL on 127.0.0.1:5432; creates .env from .env.example on first run
make db-migrate   # applies EF Core migrations as calendar_migrator
```

`.env` is untracked and holds disposable local passwords. The database creates two roles: `calendar_migrator` (owns the schema, runs migrations) and `calendar_app` (DML only; the API always connects as this role). Migrations are never applied at API startup.

Give the API its connection string with user-secrets (no secret is ever committed to `appsettings*.json`). Use the `CALENDAR_APP_PASSWORD` from your `.env`:

```sh
dotnet user-secrets set "ConnectionStrings:Calendar" \
  "Host=127.0.0.1;Port=5432;Database=calendar;Username=calendar_app;Password=dev-app-password" \
  --project backend/src/Calendar.Api
```

or set the environment variable `ConnectionStrings__Calendar`. In Development the API logs EF Core SQL commands. Integration tests need no setup beyond a running Docker daemon: they start their own throwaway PostgreSQL (the image pinned in `compose.yaml`) with `Calendar.Testing`.

> **Adding a backing service?** Re-evaluate .NET Aspire for local orchestration before wiring it into Docker Compose by hand, and add a row here. See [ADR-0016](docs/decisions/0016-local-database-provisioning.md).

> **No authentication yet.** The API is single-user and unauthenticated, so it is unsafe to expose: run it only on your own machine or a network you alone control, with no permissive CORS and no personal data ([ADR-0019](docs/decisions/0019-single-user-mode-with-authentication-deferred.md)). Write an auth ADR and implement it **before the first of**: a deployment reachable from outside the owner's machine or trusted network; a second user; or a non-browser client (mobile, desktop, CLI, integration) that has to call the API.

## Tooling

| Concern | Backend | Frontend |
| --- | --- | --- |
| Dependencies | Central Package Management (`Directory.Packages.props`) + `packages.lock.json` | pnpm workspace + `pnpm-lock.yaml` |
| Static analysis | Roslyn analyzers (`latest-recommended`) + SonarAnalyzer, warnings as errors | ESLint (typescript-eslint strict type-checked, react-hooks, jsx-a11y), `tsc` strict |
| Formatting | `dotnet format` + `.editorconfig` | Prettier |
| Unit tests | xUnit v3 (Microsoft.Testing.Platform), Shouldly, NSubstitute | Vitest, Testing Library, MSW |
| Integration tests | `WebApplicationFactory` against Testcontainers PostgreSQL (+ Respawn) | MSW-mocked API |
| Coverage | Microsoft.Testing.Extensions.CodeCoverage | `@vitest/coverage-v8` |
| Dependency updates | Dependabot (`nuget`, `docker`) | Dependabot (`npm`) |

**Repo tooling** (skill scripts in `.claude/skills/<skill>/`, other tools in `tools/<name>/`) uses .NET 10 file-based apps with folder-local analyzers and xUnit tests ([ADR-0017](docs/decisions/0017-dotnet-file-based-apps-for-repo-tooling.md)). The only exception is the bootstrap check `tools/doctor/doctor.sh`, which is shell linted with shellcheck.
