> Calendar explores how to make AI-assisted software engineering dependable. It uses the idea of delivering a planning application to develop and test ways of recording decisions, coordinating agents, checking delivery, and turning mistakes into lasting improvements. The result is both useful software and a growing body of practical engineering knowledge.

[![Documentation](https://img.shields.io/badge/Documentation-blue?style=flat-square&logo=readme)](https://mgasca.github.io/calendar/)

Monorepo for the Calendar application: a Rust backend and a web front end, with room for more UIs.

Create todo tasks from the calendar or **My tasks**, with optional date or exact-time deadlines, priority, and notes. Review Upcoming, Overdue, Completed, and No deadline lists. See the [task story and user guide](docs/stories/0003-add-todo-tasks.md). Apply the new migration with `just db migrate` before running an existing database.

| Node | `frontend/.node-version` | 24; use a version manager, since Ubuntu's apt `nodejs` is too old and lacks Corepack |
| pnpm | `packageManager` in `frontend/package.json` | Provided by Corepack (bundled with Node 24); don't install it globally |

| just | `.just-version` | The task runner ([ADR-0038](docs/decisions/0038-just-as-the-top-level-task-runner.md)); it only wraps the native commands. | jq | n/a | JSON processor used by the GitHub and CI scripts and recipes |

Run `./tools/doctor/doctor.sh` to check all of these. `just doctor` and `just setup` run the same script once `just` is installed, which is why the first run goes through the script directly.

### One-time setup on Linux / WSL

```sh
# Rust via rustup, user-local (no sudo); the toolchain in backend/rust-toolchain.toml is installed on first use
curl --proto '=https' --tlsv1.2 -sSf https://sh.rustup.rs | sh -s -- -y --default-toolchain none
sudo apt install build-essential   # C compiler and linker, if missing

# .NET SDK for the repo tools, user-local (no sudo)
curl -sSL https://dot.net/v1/dotnet-install.sh -o /tmp/dotnet-install.sh
bash /tmp/dotnet-install.sh --jsonfile global.json --install-dir "$HOME/.dotnet"   # run in the repo root
echo 'export DOTNET_ROOT=$HOME/.dotnet PATH=$HOME/.dotnet:$HOME/.dotnet/tools:$PATH' >> ~/.bashrc

# Deno for TypeScript repo tooling (run from the repo root)
curl -fsSL https://deno.land/install.sh | sh -s -- "v$(cat .deno-version)"
echo 'export PATH=$HOME/.deno/bin:$PATH' >> ~/.bashrc

# Node via fnm, which reads .node-version and switches automatically on cd
curl -fsSL https://fnm.vercel.app/install | bash -s -- --skip-shell
echo 'eval "$(fnm env --use-on-cd --version-file-strategy=recursive --corepack-enabled --shell bash)"' >> ~/.bashrc
exec bash                      # reload the shell
cd calendar/frontend && fnm install && corepack enable pnpm

# just: download the release named in .just-version from the link above, then put it on PATH

./tools/doctor/doctor.sh       # everything should be ✓
```

## Common tasks

Recipes that span both stacks run from the root (`just test`, `just check`). The rest are grouped into modules and take the module name first (`just db up`, `just docs build`); each area README lists its module's recipes. Run `just` to list them all, or `just --list <module>` for one module. To run several recipes of a module in order, stopping at the first failure, use `run`: `just db run up migrate`, or `just backend run build test -p calendar-domain` to pass arguments to the last one. An argument that does not start with `-` goes after `--`: `just image run build start -- Development`. Without `run`, only the first word is looked up in the module, so `just backend build test` runs the root `test` (both stacks).

| Task | Command |
| --- | --- |
| Check toolchain versions | `just doctor` |
| Install dependencies | `just setup` |
| Start / stop local PostgreSQL | `just db up` / `just db down` |
| Apply migrations locally (as `calendar_migrator`) | `just db migrate` |
| Run API (http://localhost:5041) | `just backend dev` |
| Run web UI (proxies `/api` to the API) | `just frontend dev` |
| Tests | `just test` |
| Lint / static analysis | `just lint` |
| Format | `just format` |
| Regenerate contract + TS client | `just contracts` |
| Everything CI runs | `just check` |

Signing in needs either a Google OAuth client ([backend README](backend/README.md#google-sign-in-setup)) or the local mode without Google ([frontend README](frontend/README.md#sign-in-without-google)).

### Local database

```sh
just db up        # starts PostgreSQL on 127.0.0.1:5432; creates .env from .env.example on first run
just db migrate   # applies the migrations as calendar_migrator (the calendar-migrate binary)
```

`.env` is untracked and holds disposable local passwords. The roles, the API's connection string and the database recipes are described in the [backend README](backend/README.md#local-database).

> **Adding a backing service?** Re-evaluate .NET Aspire for local orchestration before wiring it into Docker Compose by hand, and add a row here. See [ADR-0016](docs/decisions/0016-local-database-provisioning.md).

## Authentication and limitations

Google sign-in protects the API with a same-origin cookie ([ADR-0027](docs/decisions/0027-google-oidc-bff-session.md)). Each allowed account sees only its own events and tasks ([ADR-0041](docs/decisions/0041-per-user-data-ownership.md)): rows from before per-user ownership belong to the first email in `Auth__AllowedEmails`, which claims them at its first sign-in, and `just db seed` seeds that account. Add bearer support before enabling non-browser clients, and re-decide row-level security before sharing between users, a non-browser client with its own identity, or a background job that reads across users.

## Local container image

Run `just image build` to build `calendar:local` and `calendar:<short-git-sha>` using the Node major in `frontend/.node-version` and the pnpm version in `frontend/package.json`. The backend is built with the Rust toolchain in `backend/rust-toolchain.toml` and runs on a distroless base image as a non-root user; the image holds the `calendar-api` and `calendar-migrate` binaries, the web app and CA certificates. The image listens on port **8080**, which is also the Azure Container Apps target port.

Run `just db run up migrate` first, then `just image start`. On Linux/WSL this uses host networking to reach the loopback-only PostgreSQL port with the `calendar_app` role; port 8080 must be free and is exposed on the host network interfaces. It loads `.env` and passes the connection string through the environment. The image defaults to Production; use `just image start Development` to enable development-only behavior. Production Google sign-in requires real `Auth__Google__ClientId`, `Auth__Google__ClientSecret` and `Auth__AllowedEmails__0` settings in `.env` ([production configuration](backend/README.md#production-environment-configuration)), otherwise only anonymous endpoints are available.

In another terminal, run `just image smoke` (optionally set `BASE_URL`) to check the SPA root, `/week` deep link, `/api/health`, unknown API 404 and anonymous protected API 401. The runtime image has no healthcheck because it includes neither a shell nor an HTTP client; external platforms can probe `/api/health`.
