0072 · Use the calendar in a native desktop and browser app built with Rune

Status: planned · Date: 2026-11-20 · Issue #999 · PR #1015 · PR #1012 · PR #1013 · PR #1018 · PR #1027 · PR #1028 · PR #1029 · PR #1020 · PR #1021 · PR #1023 · PR #1024 · PR #1025 · PR #1026 · PR #1047 · PR #1048 · PR #1050

ADRs: ADR-0003 · ADR-0004 · ADR-0021 · ADR-0027 · ADR-0053 · ADR-0055 · ADR-0058 · ADR-0061 · ADR-0063 · ADR-0064 · ADR-0066 · ADR-0067 · ADR-0068

Story

As a calendar owner, I need the calendar as a native app on my Linux, macOS or Windows desktop and in my browser, with everything the web app does, so that I can plan my days in an app that feels native and the API proves it serves more than one client.

Tracked in issue #999, part of epic #998. The wording is derived from the epic and is to be confirmed by the product owner.

Background

Calendar has one UI today: the React single-page app in frontend/apps/web, with the Today, Week and My tasks views, event and task creation, editing and deletion (0004, 0043, 0047, 0048), and overdue triage with bulk actions (0007). It consumes contracts/openapi.json through a generated TypeScript client, and signs in with Google through the API’s cookie session (0005).

This story adds a second UI built with Rune, a pre-release, GPU-rendered Rust UI framework. The same Rust code runs as a desktop app on Linux, macOS and Windows and as a WASM build in the browser. It reaches parity with the React web app in staged slices, consumes the contract through a generated Rust client, and never depends on backend crates. Besides giving the owner a native app, it is the first consumer of the contract that is not the React app, so it shows whether the contract really serves other clients.

The maintainer agreed the decisions below on 2026-11-20, on the epic. Two ADRs record the larger ones: the framework, workspace, client generation, CI and hosting (#1000, ADR-0067 in PR #1012) and native sign-in (#1001, ADR-0068 in PR #1013). Both are proposed at the time of writing. This card’s adrs list gains them when they merge.

Agreed scope

  • Targets: the Linux, macOS and Windows desktop, and WASM in the browser.
  • Parity in slices: the epic closes at parity with the web app: Today, Week and My tasks; completing, reopening and deleting tasks; creating and editing events and tasks; overdue triage and bulk actions. Each slice is one issue and one PR, delivered in the order of the table under “Implementation notes”.
  • Behaviour as in the web app: each view shows what the web app shows for the same account and day, with the same rules (overdue, all-day and multi-day events, time zones). The app supplies today and timeZone from the device; the server never decides what day it is (ADR-0021).
  • Sign-in on the desktop: the existing Google flow runs in the system browser, and the session comes back to the app through a localhost loopback redirect. The app keeps the cookie session. The WASM build is same-origin and uses the browser’s cookie unchanged. The bearer scheme for non-browser clients (ADR-0027, #84) stays deferred; ADR-0068 records how this choice relates to it.
  • Workspace: a separate Cargo workspace at native/, with its own toolchain pin (Rune pins its own Rust), its own lockfile, and Clippy and rustfmt as strict as the backend’s. It has no dependency on backend/.
  • Generated client: a Rust client generated from contracts/openapi.json, regenerated by just contracts; CI fails when it is stale.
  • Recipes: just native dev opens the app on Linux/WSLg; just native test runs the headless suite; just check and CI include the native workspace; just doctor checks its toolchain.
  • CI: Linux and WASM build and run the headless tests (Rune’s element tree and PNG snapshots) on every PR. macOS and Windows build and run them on PRs that touch native/, and nightly.
  • Browser hosting: a static bundle under /native/ on the same origin as the API and the React app, served by the Vite dev server locally and by the existing static hosting in deployment.
  • End to end: the Rune app’s user flows are driven headlessly against the just e2e stack, as story 0064 requires for every flow.
  • Guidance and model: AGENTS.md, just doctor, the architecture model and the docs site describe the new UI.

Not in this story

  • Packaging, code signing and installers for any platform: follow-up #1011. The desktop app runs from just native dev or a cargo build.
  • A bearer-token scheme for mobile, CLI or third-party clients: #84 stays open.
  • Features the web app does not have. Parity is the bar; offline use, notifications and system-tray integration are not included.
  • Mobile targets (iOS, Android), although Rune may support them later.
  • Changes to the React web app, except where the contract changes for native sign-in (#1008).
  • More than three delivery sessions at once (an epic constraint, not a feature).

Dependencies

  • The card (#999) and ADR-0067 (#1000) come before the scaffold (#1002). ADR-0068 (#1001) and the generated client (#1003) come before native sign-in (#1008).
  • The views and actions build in order: #1002 → #1003 → #1004 → #1005 → #1006 → #1007. End-to-end flows (#1010) follow #1007 and #1008. macOS, Windows and /native/ hosting (#1009) follow #1002.
  • #1008 changes the contract, so the client from #1003 is regenerated in that PR.

Acceptance criteria

Decisions (#999, #1000, #1001)

  1. Given the card and ADR-0067 and ADR-0068, when the maintainer approves them, then both ADRs merge with status accepted, the architecture model lists them, and this card links them in adrs.

Scaffold (#1002)

  1. Given a Linux or WSLg machine with the pinned toolchains, when I run just native dev with the local API running, then a Calendar window opens.
  2. Given the workspace, when I run just native test, then the headless suite runs with no display and passes, and when I run just check, then it includes the native lint, build and tests.
  3. Given a PR, when CI runs, then the Linux and WASM native jobs run and are part of CI result; and given a native/ crate, then none of them depends on a backend/ crate.

Generated client (#1003)

  1. Given a change to contracts/openapi.json, when I run just contracts, then the Rust client is regenerated with the TypeScript client.
  2. Given a PR that changes the contract without the regenerated Rust client, when CI runs, then it fails and names the stale client.

Views (#1004)

  1. Given I am signed in and have events and tasks today, when I open the app, then the Today view lists the same events, open tasks and overdue tasks, in the same order, as the web app for the same day and time zone.
  2. Given the device’s time zone and date, when the app asks for a day or week agenda, then the request carries that today and timeZone, and given a day with no events or tasks, then the view shows an empty state.
  3. Given I switch to Week or My tasks, when the view loads, then it shows the same week agenda or task list as the web app, and I can move between weeks and days with the mouse and the keyboard.

Task actions (#1005)

  1. Given an open task, when I complete it, then it is shown as done in every view after a refresh; when I reopen it, then it is open again.
  2. Given a task, when I delete it and confirm, then it is gone from every view; when I cancel, then nothing changes.
  3. Given an action the server rejects (for example the task was deleted elsewhere), when it fails, then the app says so and shows the current state.

Create and edit (#1006)

  1. Given the Today or Week view, when I add an event or a task with valid fields, then it appears where the web app would show it; when a field is invalid, then the app shows the same validation message as the web app and saves nothing.
  2. Given an existing event or task, when I edit and save it, then the change shows in every view; and given the form, then it is usable with the keyboard alone and its fields have accessible names.

Triage and bulk (#1007)

  1. Given overdue tasks, when I open triage, then it lists every open overdue task in the web app’s order, and I can select rows, all loaded rows or all N overdue tasks.
  2. Given a selection, when I complete, reschedule, clear the deadline or delete in bulk, then the result per task (applied, skipped, not found) is reported as in the web app, and “all N” is refused with a conflict message if the backlog changed.

Native sign-in (#1008)

  1. Given the desktop app signed out, when I choose Sign in with Google, then my system browser opens the Google flow, and after I confirm, the app is signed in without my typing anything into it.
  • App: tested by “sign_in_redeems_the_loopback_code_and_a_restart_stays_signed_in” in tests/session.rs, against a stub API. The test plays the browser by calling the app’s loopback.
  • API: tested by “a_browser_without_a_session_signs_in_with_google_confirms_and_hands_the_session_to_the_app” in native_sign_in.rs (#1018).
  • Not yet run: against the stub provider in a real stack. #1010 runs it.
  1. Given an email that is not allow-listed, or a sign-in I abandon, when the flow ends, then the app stays signed out and says why, and no session is stored.
  • Tested by “a_refused_code_leaves_the_app_signed_out_and_says_why” and “cancel_stops_waiting_for_the_browser_and_signs_nobody_in” in tests/session.rs, and by “a_browser_that_never_comes_back_times_out_and_a_browser_that_cannot_open_says_so” in src/session/flow.rs.
  • An email that is not allow-listed never reaches the confirm page, so the loopback hears nothing. The app stops waiting after five minutes, or at Cancel, and says: “Sign-in did not finish in the browser. If your account is not allowed, the browser says so.”
  • Not yet run: the not-allow-listed case end to end. #1010 runs it.
  1. Given I am signed in on the desktop, when I restart the app within the session’s lifetime, then I am still signed in; when I sign out, then the stored session is removed and the app shows the sign-in screen.
  • Tested by “sign_in_redeems_the_loopback_code_and_a_restart_stays_signed_in” (the restart), “sign_out_calls_logout_with_the_session_and_forgets_it” and “a_401_forgets_the_stored_session” in tests/session.rs.
  • Not tested automatically: the tests use the memory store, so that they never touch a keyring. The OS credential store is exercised only by hand.
  1. Given the handover, when any step is forged or out of bounds (an expired or forged code, a wrong verifier, a redirect URI that differs at redemption, a non-loopback redirect, a cross-origin or framed confirm), then the API refuses it, and the session cookie never appears in a URL. The code is stateless (ADR-0068): within its 60 seconds it can be redeemed again, but only with the app’s verifier.
  • Tested by native_sign_in.rs (#1018): every refused start, the flow cookie, the confirm POST’s origin and framing headers, the code’s verifier, redirect and 60-second bound, and the app session never outliving the confirming session (security review of #1018).
  • Telemetry: telemetry.rs checks that no span or log carries the challenge, state, code, verifier or session.
  • App side: src/session/loopback.rs ignores stray and wrong-state callbacks, and the verifier never appears in a URL (src/session/flow.rs).

Platforms and hosting (#1009)

  1. Given a PR that touches native/, and every night, when CI runs, then macOS and Windows build and pass the headless tests.
  2. Given I am signed in to the web app, when I open /native/ in a browser with WebGPU, then the Rune app loads on the same origin and is signed in with the same cookie; and given a browser without WebGPU, then the page says so and links to the web app.

End to end (#1010)

  1. Given the just e2e stack, when the Rune app’s flows run headlessly (sign-in through the stub provider, the views, task actions, create and edit, triage), then they pass, and the architecture model’s flows name their tests.

Delivery

  1. Given the epic is complete, when I read AGENTS.md, run just doctor and open the docs site and the architecture model, then they describe the native UI, its recipes and its toolchain.
  2. Given each slice is complete, when I run just check, then it passes, including the regenerated contract and clients where the API changed.

Other decisions (not ADR-worthy)

  • One card for the epic: every slice updates this card in its own PR, rather than each slice getting a card, so the parity record stays in one place. Worker S1 owns the file; later slices add to their own sections.
  • Parity is measured against the web app, not a written spec: where the web app’s behaviour and this card disagree, the web app wins and the card is corrected, because the web app’s behaviour is what its own cards and tests already pin down.
  • Packaging is a follow-up: installers and signing need certificates and store accounts that the repository does not have yet (#1011).

System locale (#1032), delivered

Notice timeout and focus return (#1035), delivered

Lessons learned, known issues and follow-ups

  • Packaging, signing and installers: #1011.
  • Linux builds link libxkbcommon and libwayland-client: the runtime libraries alone are not enough, the -dev packages are needed (just doctor says so). Headless PNGs without a GPU render on lavapipe (mesa-vulkan-drivers).
  • Rune’s browser build script needs Python, so just native build-web runs cargo and wasm-bindgen itself (ADR-0067, ADR-0058).
  • The bearer scheme for clients that cannot keep a cookie: #84.

User guide

Planned behaviour. This section is finalised when the story is implemented.

Open the app

On the desktop, start Calendar. If you are not signed in, choose Sign in with Google. Your usual browser opens. Sign in with Google there if it asks, then choose Sign in to the Calendar desktop app. Go back to the app: you are signed in, and you stay signed in for the rest of the session, even if you restart the app.

In a browser, open the calendar’s address followed by /native/. If you are already signed in to the web app, the native app opens signed in. Your browser needs WebGPU; if it does not have it, the page tells you and links to the web app.

Plan your day

The Today, Week and My tasks views show the same events and tasks as the web app. You can add, edit, complete, reopen and delete tasks and events, and work through overdue tasks in Triage, as in the web app.

Sign out

Choose Sign out. The app forgets your session on this device. Signing out of the desktop app does not sign your browser out of the web app.

Current limitations

  • No installer yet: the desktop app is built from the repository.
  • The browser version needs WebGPU.
