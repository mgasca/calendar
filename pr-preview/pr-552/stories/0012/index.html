0012 · Architecture visualization on the documentation site

Status: implemented · Date: 2026-11-02 · Issue #178 · PR #179 · PR #180

ADRs: ADR-0000 · ADR-0010 · ADR-0017 · ADR-0022 · ADR-0023 · ADR-0025 · ADR-0028 · ADR-0039

Story

As a contributor, whether a person or another agent, I need an Architecture section on the documentation site that shows the system’s parts, how they connect, the business flows that cross them and the non-functional controls they carry, each linked to the ADRs behind it, so that I can understand the system from one place and trust that the pictures match the code and the decisions.

Tracked in issue #178. Card and ADR PR: #179; implementation PR: #180.

Background

The documentation site (ADR-0022, ADR-0023) publishes the ADR log and, since ADR-0028, the story cards. Pull requests from this repository get a preview of the site (ADR-0025). Nothing on the site showed the system as a whole: which components exist, how the web app, the API, the database, the Azure resources and CI relate, or where the 39 decisions apply. AGENTS.md describes the architecture in prose, and readers reconstructed the picture from the code and the ADRs every time.

The system is small enough to draw completely (a web app and an API in one container, a PostgreSQL database, a migrator, Google Identity, the Azure resources of one environment, GitHub Actions and the docs site), and its non-functional requirements are already written down: the session-cookie rules in ADR-0027, the least-privilege database roles in ADR-0014 and ADR-0031, the client-defined day in ADR-0021, the single read snapshot in ADR-0020, the limits and concurrency rules in the story cards, and the performance rules in AGENTS.md. A model that carries those requirements next to the components makes them visible instead of scattered.

A first machine-readable model of the whole system was drafted in FINOS CALM (nodes, relationships, controls for the non-functional requirements, seven business flows and every ADR linked) while this story was being written. It was a candidate input, not a decision: the tooling was chosen by ADR-0039, drafted as a neutral comparison in PR 0 and accepted there when the maintainer chose CALM.

Agreed scope

  • A model file under docs/ is the source of truth. Every diagram on the site is derived from it at build time. Nothing is drawn by hand and left to drift from the code or the decisions.
  • An Architecture section on the documentation site, built from the model and published with the ADRs and the stories, including the pull-request previews. It holds:
    • a system-context view: the people, the calendar system, Google Identity, GitHub and Azure;
    • a container and deployment view: web app, API, database, migrator, the single container image, the Container Apps environment, the Key Vaults, the registry, monitoring and the docs site;
    • sequence diagrams of a few business flows: Google sign-in, viewing today, adding an event, ticking a task off, overdue triage, applying database migrations and publishing the decision log;
    • the non-functional controls (authentication, least-privilege data access, time correctness, read consistency, concurrency, request limits, observability, secrets, durability, query and client performance, accessibility) shown on the elements they apply to;
    • a link from every element to the ADRs it depends on, using the stable adr/NNNN/ routes, and from each flow to its story card.
  • Validation is a gate. The model is validated in just check and in CI, and the docs build fails on an invalid model (a schema error, a dangling reference, an ADR number that does not exist). The tool is pinned like the rest of the toolchain (ADR-0010); if it is a separate binary, just doctor checks it.
  • An ADR chooses the tooling. ADR-0039 weighs FINOS CALM, C4 with the Structurizr DSL, hand-written Mermaid in Markdown, LikeC4 and PlantUML or D2 against four drivers: a validatable model rather than pictures, traceability to ADRs and non-functional requirements, fit with the pinned toolchain, and rendering inside the Starlight site. It was drafted as a neutral comparison and accepted in PR 0 when the maintainer chose FINOS CALM.

Not in this story

  • Generating the model from the code (reverse engineering). The model is written by hand and reviewed like an ADR.
  • Diagrams of cost, capacity or runtime telemetry. The section describes structure, flows and requirements, not operations.
  • Changing the ADR or story-card formats, or how they are published. The Architecture section is added next to them.
  • A pattern library or reuse of the model outside this repository. If the chosen tool supports patterns or a shared hub, that is a later story.
  • Keeping the model and the ADR index in step automatically. The model lists the ADRs it links; a test that every linked ADR exists is in scope, a tool that updates the model when an ADR changes status is not.

Dependencies

  • ADR-0039 was approved in PR 0, before the model and the rendering were merged (PR 1). Its accepted status only reached main later (see criterion 7).

Acceptance criteria

  1. Given the published documentation site, when I open the Architecture section, then I see a system-context view, a container and deployment view, sequence diagrams of the business flows listed in the scope, and the controls on the elements they apply to. Pages rendered from the model (renders an overview, the container view, …, collapses the context diagram …, nests the container diagram …, draws a flow as a sequence diagram …) and every page built with a Mermaid block and its table (published architecture). The diagrams were not rendered in a browser by the implementing agent (no browser was available); the PR preview is where that was checked.
  2. Given any element or flow in the Architecture section, when I look for the decisions behind it, then it links to the ADRs it depends on at their adr/NNNN/ routes, and a flow links to its story card. Built pages carry the ADR and story hrefs (published architecture); component and flow bodies link decisions and stories (gives a component its interfaces, relationships, controls and decisions, draws a flow …).
  3. Given a pull request from this repository that changes the model, when CI runs, then the model is validated and the pull-request preview shows the regenerated diagrams. The Docs site job (the Frontend job until #274) runs pnpm --filter @calendar/docs validate:architecture before the tests and build (.github/workflows/ci.yml), and the existing preview publication covers the generated pages. Checked on PR 1’s ADR preview; no automated test exercises the preview.
  4. Given a model with a schema error, a dangling reference or an ADR number that does not exist, when just check runs, then it fails and names the problem. calm validate fails on a broken fixture (calm validate gate) and the loader rejects every dangling reference (rejects …, 22 cases). just lint runs the first through just docs architecture; the docs tests and build run the second.
  5. Given the chosen tool, when just doctor runs on a machine where the pinned version is missing or different, then it says so, unless the tool is a workspace dependency installed by pnpm install. @finos/calm-cli is a devDependency of frontend/apps/docs, pinned by frontend/pnpm-lock.yaml and installed by pnpm install --frozen-lockfile, so just doctor has nothing to check. No test.
  6. Given the Architecture section, when it is read on a phone or with a screen reader, then every diagram has a text alternative (a table or list of the same elements and relationships), and the pages pass the site’s existing accessibility lint. Every built page with a diagram also has a table (published architecture). The docs app has no accessibility lint (jsx-a11y applies to apps/web only), so that part of the criterion is not checked; the pages are plain Starlight Markdown.
  7. Given ADR-0039, when the maintainer approves the decision, then it is accepted in that same PR before it merges, and the implementation PR references it. Partly met on #179: the maintainer chose FINOS CALM there, but the commit “ADR-0039 accepted” was pushed two minutes after the PR had merged, so main kept proposed. Nobody noticed until 2026-11-05, when the maintainer confirmed the decision and the same text was applied to the ADR and its model entry. PR 1 references the ADR. No automated test.
  8. Given the change is complete, when I run just check, then it passes, including the model validation. CI runs every part of just check on PR 1. Locally the implementing agent ran the frontend gates (format:check, lint, typecheck, test), validate:architecture, build-docs and just --fmt --check; just tools adr could not run on that machine (its SDK rejects the #:include directive), so the Tooling job is the check for it.

Other decisions (not ADR-worthy)

  • The model lives in docs/architecture/, next to docs/decisions/ and docs/stories/, because it is documentation that reviewers read and the site builds from, not product code.
  • Diagrams are generated at build time, never committed as images. The model is reviewable text; a committed image would be a second source of truth. Mermaid renders in the browser (astro-mermaid), so the build needs no headless browser and previews and production render the same source.
  • Every diagram has a text alternative. The same generation step emits a table of the diagram’s elements and relationships, so the section is usable without the picture.
  • The Architecture section lists the ADRs it links in one place (the Decisions table on the overview), so a reader can see which decisions the model covers and which elements depend on each.
  • Views are declared in the model’s metadata (metadata.views.context and .containers, each a list of node ids), because CALM has no view concept and the choice of what a diagram shows is a documentation decision, kept with the model rather than in code.
  • Colour encodes ownership, not node type. Each node is a person, built in this repository, hosting or tooling we configure (Azure, GitHub), or an external service we only use (Google). Actors and the members of a composition get it by derivation; everything else declares metadata.ownership, and the docs build fails on a node with neither. A one-line legend with swatches sits under each diagram and the element tables carry the same label, so the colour is never the only carrier. The flow diagrams got the same treatment in story 0016.
  • Component pages are hidden from the sidebar. Twenty-three entries would swamp the navigation; the Components index lists them and search finds them.
  • The model’s ADR list must match the decision log exactly (file, title, status, URL), checked by the docs build. The cost is one edit to the model when an ADR changes status; the benefit is that the Decisions table on the site can never lie.

Testing

  • architecture.test.ts: parsing of every element kind; 22 rejected mutations (dangling nodes, interfaces, relationships and views, out-of-order steps, ADR file/title/status/URL drift, unknown stories, unmapped requirements); diagram text helpers; the rendered pages; and the calm validate gate on a broken fixture (src/lib/fixtures/invalid.architecture.json, 30 s timeout because the CLI takes seconds to start).

  • build.test.ts (published architecture): every page is built, the sidebar lists the section and the flows but not the component pages, every page with a diagram has a <pre class="mermaid"> and a table, and component and flow pages carry the ADR and story hrefs.   • CI: validate:architecture in the Docs site job, the unit tests, the build and the post-build verification.

Lessons learned, known issues and follow-ups

  • The reference check earned its keep immediately: it found two ADR titles in the model that had drifted from the decision log (0017 and 0019) before the first build.
  • astro-mermaid and a custom unified() processor coexist: the integration recreates the processor with its own plugins added, so remarkDocLinks kept working. Place it before Starlight in integrations.
  • The Mermaid client bundle is large: Vite warns about a 660 kB chunk; the heavy renderers (Cytoscape, KaTeX) are split into separate lazy chunks that flowcharts and sequence diagrams do not load. Measured on the build output, not profiled in a browser.
  • Measured: the docs build went from 56 to 89 pages (33 architecture pages) and takes about 25 s on the implementing agent’s machine; the docs unit tests take under 5 s including the CLI test.
  • erasableSyntaxOnly is on in the frontend TypeScript config, so classes cannot use constructor parameter properties; assign fields explicitly.
  • Not verified by the implementing agent: diagram rendering in a browser (no browser was available), the preview workflow on this PR before it ran, and just tools adr locally (SDK mismatch; CI runs it).
  • Follow-ups: a story for keeping the model current could add a CI check that every node named in AGENTS.md’s architecture section exists in the model; the model’s metadata.adrs must be edited by hand when an ADR changes status (deliberately, see the decision above).

User guide

Reading the architecture

Open the documentation site and choose Architecture in the sidebar. The Overview shows who uses the calendar and which outside services it depends on, with a table of the same elements beneath the diagram, and ends with a table of every decision (ADR) and the parts that depend on it. Choose Containers and deployment to see the parts that run (the web app and API in their container, the database, the migrator, the Azure resources and the documentation site) and how they connect. Choose Components for the list of every part; each part’s page gives its interfaces, its relationships, the controls it must satisfy, such as the sign-in rules or the limits on a request, and links to the decisions and stories behind it. Controls lists every non-functional requirement and where it applies. Under Flows, choose an activity such as Google sign-in or Triage all overdue tasks to follow it step by step across the parts, as a sequence diagram with a numbered table of the same steps. Every diagram has a table beneath it with the same information, so the pages can be read without the pictures.

To change the architecture, edit docs/architecture/calendar.architecture.json (the Edit page link on every architecture page opens it). Run just docs architecture to validate it against the CALM schema and just docs build to rebuild the pages; both run in just check.
