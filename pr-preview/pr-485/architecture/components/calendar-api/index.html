Calendar API

Type: service

ASP.NET Core minimal API on .NET 10 (backend/src/Calendar.Api) with a framework-free Calendar.Domain (time-zone and day-inclusion rules) and Calendar.Infrastructure (EF Core 10 on Npgsql, SQL forms of the domain rules). Serves events, tasks, day and week agenda read models and Google sign-in with a cookie session; also serves the SPA’s static files and index.html fallback. Every endpoint requires an authenticated user except health and sign-in.

Controls

authentication

Google OpenID Connect with a backend-for-frontend cookie session (ADR-0027). The fallback authorization policy requires an authenticated user on every endpoint; only health, the sign-in endpoints and the SPA static files are anonymous. Only verified emails on the allow-list may sign in.

Requirement schema: https://raw.githubusercontent.com/mgasca/calendar/main/docs/architecture/controls/authentication.requirement.json

  • identity-provider: Google OpenID Connect (Microsoft.AspNetCore.Authentication.Google), callback /api/auth/callback/google
  • pattern: Backend-for-frontend: the API holds the OAuth client secret and issues a same-origin cookie; the browser never sees tokens
  • fallback-policy: RequireAuthenticatedUser on every endpoint (AddAuthorization FallbackPolicy)
  • anonymous-endpoints: GET /api/health, GET /api/auth/login, GET /api/auth/callback/google, SPA static files and index.html fallback, OpenAPI document (Development only)
  • allow-list:
    • source: Auth:AllowedEmails (Key Vault secrets allowed-email-N → Auth__AllowedEmails__N in Azure; user-secrets locally)
    • requires-verified-email: true
    • comparison: case-insensitive exact match; failure redirects to /signin?error=access_denied without creating a session
  • session-cookie:
    • http-only: true
    • same-site: Lax
    • secure: Always outside Development (SameAsRequest in Development)
    • lifetime: 8 hours absolute
    • sliding-expiration: false
    • key-storage: ASP.NET Data Protection key ring persisted in the database (data_protection_keys table), application name ‘Calendar’
  • open-redirect-protection: returnUrl must be a local absolute path (no //, no backslash, no control characters) on both server (ApiAuthentication.LocalReturnUrl) and client (safeReturnTo)
  • unauthenticated-api-response: 401 (or 403) for /api/* instead of a redirect; the client raises calendar:unauthorized and routes to /signin with the current URL
  • adrs: https://mgasca.github.io/calendar/adr/0027/

per-user-data-isolation

Every event and task belongs to one user (owner_id). CalendarDbContext applies a global query filter keyed by the signed-in user, so every read, count, ExecuteUpdate and ExecuteDelete is scoped by default; a context with no user sees nothing; another user’s id answers 404 (ADR-0041).

Requirement schema: https://raw.githubusercontent.com/mgasca/calendar/main/docs/architecture/controls/per-user-data-isolation.requirement.json

  • owner-column: events.owner_id and tasks.owner_id: non-null uuid, FOREIGN KEY users(id) ON DELETE RESTRICT
  • identity-key: users keyed by Google’s sub claim (unique), email lower-cased and unique; resolved or created in the Google OnCreatingTicket event (UserDirectory): by subject, else by email among rows without a subject, else the unclaimed legacy placeholder for the first allow-listed email, else a new row
  • scoping-mechanism: EF Core HasQueryFilter(x => x.OwnerId == CurrentUserId) on CalendarEvent and TodoTask, where CurrentUserId is a property of the context instance fed by the scoped ICurrentUser (HttpCurrentUser reads the urn:calendar:user-id claim); SaveChanges refuses an added row owned by anyone else
  • fail-closed: No signed-in user (FixedCurrentUser.None, the migrator context, the design-time factory): the filter matches no rows; IgnoreQueryFilters is used only in tests
  • legacy-owner: The PerUserOwnership migration inserts users row 11111111-1111-1111-1111-111111111111 and backfills every existing event and task to it; the first sign-in or seed run by Auth:AllowedEmails[0] claims it
  • session-claim: The users.id travels in the cookie as urn:calendar:user-id; OnValidatePrincipal rejects and signs out a cookie without it (401 to API callers), so sessions issued before ADR-0041 end once
  • cross-user-response: 404 for GET /api/events/{id}, GET/complete/reopen/DELETE /api/tasks/{id}; notFound outcome in POST /api/tasks/bulk by ids; filter-based bulk actions and agenda counts only ever cover the caller’s rows
  • client-supplied-user: false
  • tests: backend/tests/Calendar.Api.Tests/Endpoints/OwnershipTests.cs (two users, every endpoint), backend/tests/Calendar.Api.Tests/UserDirectoryTests.cs (lookup order, legacy claim), backend/tests/Calendar.Api.Tests/OwnershipMigrationTests.cs (backfill), backend/tests/Calendar.Api.Tests/Endpoints/SessionAndSeedTests.cs (old cookie, seed scheme), backend/tests/Calendar.Api.Tests/SchemaTests.cs (owner columns, keys, indexes)
  • adrs: https://mgasca.github.io/calendar/adr/0041/

time-correctness

The client’s IANA time zone and local date define the day; the server never decides what day it is (ADR-0021). Instants are UTC DateTimeOffset with an end-exclusive span plus the IANA zone id, all-day values are end-exclusive floating dates, and DST gaps and overlaps are handled in one place (ADR-0018).

Requirement schema: https://raw.githubusercontent.com/mgasca/calendar/main/docs/architecture/controls/time-correctness.requirement.json

  • day-defined-by: The client: every endpoint that judges overdue or upcoming takes today/date + timeZone, validated with FieldErrors.RequireDate / RequireTimeZone and marked required in OpenAPI (RequireQueryParameters)
  • required-parameters: GET /api/agenda/day: date, timeZone, GET /api/agenda/week: date, timeZone, today, GET /api/tasks?view=upcoming|overdue: today, timeZone, POST /api/tasks/bulk filter: today, timeZone, expectedTotal
  • time-zone-ids: IANA only; legacy aliases mapped to canonical ids from tzdata’s backward table (IanaAliases); ’+’ must be sent as %2B
  • rejected-time-zone-ids: Windows ids, localtime, unknown or hostile ids
  • instants: DateTimeOffset with an explicit offset (ExplicitOffsetConverter; missing offset → 400), normalised to UTC and stored as timestamptz; tasks have DueDate XOR DueAt (check constraint ck_tasks_due_date_xor_due_at)
  • floating-dates: DateOnly stored as date; all-day events are [startDate, endDate) end-exclusive
  • date-range: Years 1900–2200 (ADR-0024); anything else is 400 on the API and notFound in the router
  • dst:
    • non-existent-local-time: Rejected on the client (deadlineInstants / event form) and server
    • ambiguous-local-time: The user chooses the occurrence (UTC offset)
    • skipped-date: An empty day window (e.g. Pacific/Apia 2011-12-30); the week view shows a note
    • day-window: DayWindow: [local midnight D, local midnight D+1) as UTC; 23 h and 25 h days handled; a non-existent midnight starts at the first valid instant
  • server-clock: Injected TimeProvider (TimeProvider.System in the app, FakeTimeProvider in tests), used only to stamp completedAt
  • banned-apis: DateTime.Now, DateTime.UtcNow, DateTime.Today, DateTimeOffset.Now, DateTimeOffset.UtcNow, TimeZoneInfo.Local
  • adrs: https://mgasca.github.io/calendar/adr/0018/, https://mgasca.github.io/calendar/adr/0021/, https://mgasca.github.io/calendar/adr/0024/, https://mgasca.github.io/calendar/adr/0036/

read-consistency

Every agenda read (day or week) is one read-only REPEATABLE READ snapshot, so a task completed or an event added between its queries cannot appear in some lists and not others (ADR-0020). The week endpoint reuses the same range-based builder with the same fixed number of queries (ADR-0024).

Requirement schema: https://raw.githubusercontent.com/mgasca/calendar/main/docs/architecture/controls/read-consistency.requirement.json

  • isolation-level: REPEATABLE READ
  • read-only: true
  • queries-per-read: Four range queries (all-day events, timed events, due tasks, overdue tasks + two counts) whatever the range length; AsNoTracking projections, no N+1
  • single-rule-implementation: Calendar.Domain.Agenda.DayInclusion decides per-day membership in memory; Calendar.Infrastructure.Queries holds the SQL forms; *AgreementTests prove they agree, and a week/day agreement test proves days[i] of a week equals the day agenda
  • adrs: https://mgasca.github.io/calendar/adr/0020/, https://mgasca.github.io/calendar/adr/0024/

concurrency-control

Writes use optimistic concurrency on the PostgreSQL xmin system column (ADR-0015) and report conflicts as 409. Set-based bulk actions on ‘all N overdue’ run in a SERIALIZABLE transaction guarded by the client’s expected count.

Requirement schema: https://raw.githubusercontent.com/mgasca/calendar/main/docs/architecture/controls/concurrency-control.requirement.json

  • strategy: Optimistic
  • token: xmin (xid) concurrency token on events and tasks
  • conflict-status: 409
  • idempotent-operations: POST /api/tasks/{id}/complete, POST /api/tasks/{id}/reopen, DELETE /api/tasks/{id} (404 treated as already deleted by the client)
  • bulk-filtered-writes:
    • isolation-level: SERIALIZABLE
    • guard: The open-overdue count for the client’s today/timeZone must equal filter.expectedTotal
    • on-mismatch: Roll back and return 409 ‘The overdue task count changed’; serialization failures and deadlocks also map to 409
  • client-behaviour: A 409 on a toggle triggers a refetch; the triage view asks the user to review the new count and retry; per-id bulk results report applied, skipped or notFound
  • adrs: https://mgasca.github.io/calendar/adr/0015/

request-limits

All input is validated into RFC 9457 problem details with per-field errors; list endpoints use opaque keyset cursors with bounded page sizes; bulk requests are capped.

Requirement schema: https://raw.githubusercontent.com/mgasca/calendar/main/docs/architecture/controls/request-limits.requirement.json

  • error-format: application/problem+json (RFC 9457); binding failures become 400 via BadRequestExceptionHandler
  • validation-status: 400
  • field-limits:
    • title: required, trimmed, ≤ 200 chars
    • location: ≤ 200 chars
    • notes: ≤ 4000 chars
    • priority: low | medium | high (default medium)
    • event-end: must be after start
    • task-deadline: due date XOR due instant
  • pagination:
    • style: Keyset, every comparison in SQL, limit + 1 fetched to detect the next page
    • default-limit: 50
    • max-limit: 200
    • cursor: Opaque base64url JSON tied to its view
    • malformed-cursor-status: 400
  • bulk:
    • max-ids: 500
    • filter-views: overdue
  • agenda-overdue-limit: 20
  • adrs: https://mgasca.github.io/calendar/adr/0002/, https://mgasca.github.io/calendar/adr/0020/

observability

The container exposes /api/health for startup, liveness and readiness probes; console logs and probe results go to the Log Analytics workspace, and Application Insights is provisioned in the same workspace.

Requirement schema: https://raw.githubusercontent.com/mgasca/calendar/main/docs/architecture/controls/observability.requirement.json

  • health-endpoint: GET /api/health → { “status”: “ok” } (anonymous; starts without a database connection string)
  • probes:
    • type: Startup
    • period-seconds: 5
    • failure-threshold: 60
    • initial-delay-seconds: 1
    • type: Liveness
    • period-seconds: 10
    • failure-threshold: 3
    • type: Readiness
    • period-seconds: 5
    • failure-threshold: 3
  • logs: Container Apps appLogsConfiguration → Log Analytics workspace law-calendar-
  • log-retention-days: 30
  • telemetry: Application Insights appi-calendar- (workspace-based)
  • audit-logs: Key Vault AuditEvent diagnostics for the app and ops vaults
  • structured-logging: CA1848 requires LoggerMessage source-generated logging methods
  • adrs: https://mgasca.github.io/calendar/adr/0029/, https://mgasca.github.io/calendar/adr/0032/
