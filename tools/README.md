# Repo tooling

Every script in this repo is a .NET 10 *file-based app* (`dotnet run x.cs`, no project file), kept in `tools/<name>/` or in the skill folder it belongs to, with that folder's own analyzers, `.editorconfig` and xUnit tests ([ADR-0017](../docs/decisions/0017-dotnet-file-based-apps-for-repo-tooling.md)). The only exception is `tools/doctor/doctor.sh`, a bootstrap check that must run without the SDK. Don't write new tooling in Python, Node or shell. Read this page before writing or fixing a tool.

## Layout and discovery

- A tool is `tools/<name>/<name>.cs` (the entry point, with a `#!/usr/bin/env -S dotnet run` line and a usage comment), one or more `#:include`d implementation files, and `tests/<name>.tests.cs`. Copy `tools/tool-versions/` as the pattern, including `tests/Directory.Build.props`.
- `just tools test` runs every `*.tests.cs` under the `tool_dirs` list in `tools/mod.just` and `dotnet format whitespace --verify-no-changes` on each directory. `tools` is in the list, so a new `tools/<name>/` is checked automatically. A tool inside a skill folder must be added to `tool_dirs` by hand, or neither its tests nor CI validate it (the gap behind #190 and #209). After adding one, check that `just tools test` prints its test file.
- Package pins (`#:package` directives and `Directory.Build.props`) must match `backend/Directory.Packages.props`; `just tools versions` fails on drift and `just tools versions --fix` rewrites them. The first run of a tool writes `packages.lock.json` next to it: commit it. CI restores in locked mode.

## SDK and build gotchas

- `#:include` needs .NET SDK **10.0.300 or later**. On 10.0.1xx or 10.0.2xx every tool that uses it fails with `Unrecognized directive 'include'` before compiling. `just doctor` checks the SDK that `dotnet --version` resolves at the repo root; `backend/global.json` does not cover the tools.
- File-based apps default to `PublishAot=true`, so reflection-based `System.Text.Json` fails analysis. Use `JsonDocument`, `Utf8JsonWriter` or a source-generated `JsonSerializerContext` (see `tools/seed-dev/SeedPlan.cs`).
- Warnings are errors, with the same analyzers as the backend. The traps that bite most: S103 (lines over 140 characters, which nothing fixes automatically), IDE0007/IDE0008 (`var` only when the type is apparent on the right-hand side), IDE0305 (use collection expressions instead of `.ToList()` into a typed variable), CA1307 (pass a `StringComparison`), S127 (don't change a `for` loop variable in its body), S4036 (start processes by absolute path), S6966 (await the async console methods). The first `dotnet run` compiles the file and takes a few seconds; later runs are cached.

## Formatting a tool

`dotnet format` doesn't accept file-based apps. To apply code fixes, convert the tool into a scratch project inside its own directory, so its `Directory.Build.props`, `.editorconfig` and `SonarLint.xml` still apply, format that, copy the code back and keep the `#!`/`#:` header lines:

```bash
cd tools/<name> && mkdir -p .scratch && cp *.cs .scratch/ && cd .scratch && dotnet project convert <name>.cs
```

Then `dotnet format` inside `.scratch`, copy the formatted bodies back and delete `.scratch`. The whitespace check that CI runs (`dotnet format whitespace --folder --verify-no-changes <dir>`) does accept file-based apps, so run it last.

## Reporting what a tool's checks covered

A scratch build that drops the folder's `Directory.Build.props`, `.editorconfig`, `SonarLint.xml` or package settings can pass locally and fail the CI analyzers (#185). When you report verification, name the directory, the command, and whether `just tools test` discovered the tests.

## ci-timings

`tools/ci-timings/` samples how long a workflow's jobs and steps take from the runs GitHub keeps (`just tools ci-timings --job Frontend`, needs `gh auth status` to pass). Only completed, successful runs count; `--branch <name>` keeps only the runs of one branch, which is how a PR measures itself against `main`. It prints Markdown tables for a benchmark record (`docs/benchmarks/README.md`): one row per job with min, median, p90 and max, and, for each `--job`, one row per step. `--superseded` reports on cancelled runs instead. It pairs each cancelled pull request run with the next run of its branch. It then times how long that run waited for its first job and for all of them, when the old run's runners heard of the cancel (bounded by the steps they still started and the first step that ended cancelled), and when the old run ended. Control rows cover pull request runs that superseded nothing (record 0008). `--created "<2026-11-06T16:15:00Z"` passes a date range to `gh run list`, so a record's before window can be reproduced after newer runs have joined the list. Run that one with `dotnet run tools/ci-timings/ci-timings.cs -- …`, because the recipe does not quote its arguments (#345). `CiTimings.cs` holds the parsing, the pairing, the nearest-rank statistics and the rendering, which the tests cover; the entry file only calls `gh`.

## handover-watch

`tools/handover-watch/` is the watch of the `issue-handover` skill: `just tools handover-watch <issue>` prints what is new on an issue and its delivery PRs since the last run and records it, so a handover tick is one call (needs `gh auth status` to pass). A delivery PR is one that cross-references the issue with `Closes`, `Fixes`, `Resolves` or `Refs` before its number in the body and was opened by the owner, a member or a collaborator, whether open, closed or merged. A bare mention in prose does not count, nor does a PR from someone without write access (anyone can write `Refs #N`); `--pr N` adds a PR either rule leaves out. It covers the issue's comments, each PR's conversation comments, inline review comments and submitted reviews, and each PR's state when first seen and on every change. An empty `COMMENTED` review (the wrapper GitHub puts around inline comments) and a pending review are left out; an approval with an empty body is kept.

The first line names the watched PRs with their state and says how many items are new, or `nothing new`. Each item is a header line (`=== kind:id · #N` or `PR #N` `· author · agent-footer: yes|no · …`), its link, and its body indented by two spaces, so no body line can pass for a header; control characters such as terminal escapes and bidirectional overrides are replaced, and a header is always one line, whatever a file path or login holds. `agent-footer: yes` means the last non-blank line starts with `🤖 Generated with` and is not quoted, a heuristic rather than authentication. What was printed is appended to `.plan/handover-watch/<issue>.seen` (git-ignored, one `kind:id` per line, in the checkout that holds the tool, so two worktrees watching one issue do not consume each other's items), after printing, so a failed run prints again rather than loses an item. `--peek` prints without recording; deleting the file starts over. Edits to an item already printed and CI check results are not reported. `HandoverWatch.cs` holds the argument parsing, the PR filter, the seen-ID logic and the rendering, which the tests cover; the entry file only calls `gh`, with the per-PR requests in parallel (at most six `gh` processes at once).

## agent-hooks

`tools/agent-hooks/` is the set of Claude Code hooks wired in `.claude/settings.json` ([ADR-0042](../docs/decisions/0042-layered-agent-guidance-and-hooks.md)): it denies discarding unstaged work, public posts with private details, edits of generated files and a `git push` to a branch whose PR is merged or closed; asks before the shared database is touched from a linked worktree; and reports over-long C# lines, a stale API contract and a PR to `main` that names no issue it closes or refers to. The code is one file per guard or check (`BashGuard.cs`, `EditGuard.cs`, `LineLengthCheck.cs`, `ContractCheck.cs`, `PullRequestLinkCheck.cs`), plus `ShellCommand.cs` (command splitting that keeps quoted, `$(...)` and heredoc text whole, #355), `PullRequestLookup.cs` (asks `gh pr view` for a PR's state, or its base and body), `ExternalCommand.cs` (runs a process with a time limit), `HookRunner.cs` (subcommand dispatch), `GitProbe.cs` behind `IRepoProbe.cs` (questions asked of git) and `HookProtocol.cs` (the hook JSON in and out); each tested class has a matching `tests/<Class>Tests.cs`, included by the one test app `tests/agent-hooks.tests.cs`. Each subcommand reads the hook JSON on stdin, so you can try one by hand:

```bash
printf '{"tool_name":"Bash","tool_input":{"command":"git restore AGENTS.md"},"cwd":"%s"}' "$PWD" | dotnet run tools/agent-hooks/agent-hooks.cs -- pre-bash
```

The public-post guard covers `gh issue` and `gh pr` `create`, `comment`, `edit` and `review`, and any `gh api` call with a field or `--input`. It scans the command's words, and in place of a body source's local path, what the source holds. The sources are the file of `--body-file`, `gh api --input` and a typed field's `@` value (`-F body=@file`); for `-`, it reads the command's heredoc. A raw field (`-f body=@x`) is sent as written, so it is scanned as written. So is a word starting with `-` after one of these options, because an earlier option may have taken the option as its value. The hook sees the command before it runs, so it reads a source through what the command itself states (#374): it expands `~`, `$NAME` and `${NAME}` from earlier assignments in the command (`S=…`, `export S=…`), then from its own environment; it reads a file that an earlier `cat` or `tee` heredoc, or `echo` or `printf`, writes (`>`, `>>`); and for `-` it reads a `< file` redirect, the files of a `cat` piped in, or the words of any other command piped in (`jq -n '{body: …}' | gh api … --input -`). That model can differ from what the shell does, so whatever it contributes is scanned together with the words that name the source and the file as it is on disk, never in their place. Only a literal file read from disk, or a heredoc, replaces the words. A write whose text holds a `$` or a backtick (which the shell may expand), or any other command's output redirected to a file, is not modelled. When it still cannot read a source, such as a variable the agent's shell set in an earlier call or a `$(...)` path, it scans the words that name it instead, so only a path that itself looks private is caught. A file reads as text only when it is a regular file of at most 1 MiB with no NUL byte. An empty file, a pipe, a device, a larger file or a binary one reads as empty, so an upload sent with `gh api --input` is neither read whole nor denied on its bytes; the line-length check reads files the same way (#355, #369, #374).

The stale-contract check at stop counts a file as changed only while it still differs from `origin/main`, so a squash-merged branch stops tripping it. It passes when `contracts/openapi.json` was written after every changed contract source (any API build regenerates it, so an unchanged contract no longer blocks every turn), and the same holds for `schema.gen.ts` against the contract; a deleted source still blocks (#254).

The push guard runs `gh pr view <branch> --json number,state` (10 s limit) only for a `git push`. It checks the destination branch of each refspec: the current branch for a bare push or `HEAD`, or the one an earlier `git switch -c` or `git checkout -b` in the same command created, so the remedy it names passes. A merged or closed PR denies; it lets the push through whenever gh has no answer (no PR, no gh, not signed in, offline, timed out) and for a detached HEAD, a delete, a dry run, `--all`, `--mirror` or tags only (#293).

The PR link check is an inform hook and Claude Code only ([ADR-0044](../docs/decisions/0044-claude-first-agent-automation.md)); the `Closes` rule in `AGENTS.md` is what other agents follow. On `gh pr create` and on `gh pr edit` with a new body, it adds a note, never a decision, when the PR targets `main` and the body (`--body`, the file of `--body-file`, or the heredoc of `--body-file -`) has neither a closing keyword (`Closes`, `Fixes`, `Resolves`) nor `Refs` before an issue. On a retarget (`gh pr edit --base main`) it notes a body without a closing keyword, even with `Refs`, because a stacked PR gets its `Closes` then. A create without `--base` targets `origin/HEAD` (`main` when git cannot tell). An edit asks `gh pr view [<pr>] --json number,baseRefName,body` (3 s limit; it took 0.7–0.9 s when measured) for the base or the body it leaves as they are. When the body cannot be known (`--fill`, `--template`, `--web`, an unreadable file) or gh has no answer, there is no note (#321).

Exit 0 with JSON is a decision or a note; exit 2 with stderr is a usage error; any other failure (for example an SDK below 10.0.300) is non-blocking for Claude Code, and the rules in `AGENTS.md` still apply by hand. Each handler carries an `if` filter (`Bash(git *)`, `Edit(**/*.cs)`, …) so unrelated commands and edits start no process. Personal overrides go in the git-ignored `.claude/settings.local.json`. Revisit the hooks when their latency is still felt in sessions, when Claude Code documents native nested `AGENTS.md` loading (drop the `CLAUDE.md` shims), or when a rule in `AGENTS.md` is ignored repeatedly (promote it to a hook). During the Claude-first period of [ADR-0044](../docs/decisions/0044-claude-first-agent-automation.md), new ask and inform hooks and other automation may be Claude Code only; the period is revisited when the maintainer states it, and ending it is a new ADR.
