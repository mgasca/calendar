0064 · Test every user flow end to end and prove it is observable

Status: implemented · Date: 2026-11-13 · Issue #728 · PR #740 · PR #750 · PR #746 · PR #765 · PR #769 · PR #767 · PR #772 · PR #793 · PR #796 · PR #800 · PR #798 · PR #841 · PR #832 · PR #876 · PR #909 · PR #899 · PR #877 · PR #901 · PR #903 · PR #931 · PR #929 · PR #940

ADRs: ADR-0008 · ADR-0021 · ADR-0027 · ADR-0030 · ADR-0039 · ADR-0058 · ADR-0061 · ADR-0062 · ADR-0063 · ADR-0064

Story

As the calendar owner, I need every flow people use to be exercised end to end in a real browser, and each run to leave a trace, logs and request metrics that carry no personal data, so that a regression or a blind spot in production shows up before a user finds it.

Tracked in epic #728; this card is PR 0, issue #729. The scope below is the epic’s “Approved decisions”, agreed with the maintainer on 2026-11-13.

Background

The architecture model (docs/architecture/calendar.architecture.json, ADR-0039) describes nine flows. Seven are things a person does in the web app: sign in, view today, add an event, edit an event, edit a task, tick a task off and triage overdue tasks. Each is covered today by Vitest component tests with MSW (ADR-0008) and by Rust API tests on Testcontainers PostgreSQL, but nothing drives the built web app, the API and the database together in a browser. ADR-0008 deferred Playwright end-to-end tests “until there are real user flows”; those flows now exist.

Nothing shows what a flow did once it ran either. What exists today:

  • API logs: tracing with tracing-subscriber’s plain-text formatter at INFO, to standard output (calendar-api/src/main.rs). No request spans, trace ids, JSON output or metrics. tower-http is used only for ServeDir.
  • Azure: Container Apps sends console logs to the Log Analytics workspace law-calendar-<suffix> (30-day retention). Application Insights appi-calendar-<suffix> is provisioned workspace-based (infra/modules/monitoring.bicep), but the container app gets no connection string and the API sends it nothing. Key Vault audit events go to the same workspace.
  • Health: GET /api/health backs the startup, liveness and readiness probes. Stale PR #120 added a database readiness endpoint, alerts and budgets for the .NET backend; none of it is on main, and it is closed as superseded.
  • Web: no telemetry.
  • Local: Docker Compose runs PostgreSQL only; ADR-0016 (now superseded by ADR-0063) deferred Aspire until a second backing service.
  • Sign-in tests: the Rust API tests already run the Google round trip against an in-process fake of Google’s token and userinfo endpoints (calendar-api/tests/google_sign_in.rs: allow-listed sign-in, denial, foreign callback, Secure cookies behind the proxy). In the running API, Google’s endpoints are injectable only through AppOptions in tests, and the accepted issuers are a constant.

This story makes each user-facing flow a browser test on a real stack and makes the same run prove the flow is observable: one trace from the browser click to the database, logs carrying that trace id, request metrics, and no personal data in any of them. It builds on stories 0001 to 0005 (the flows), 0021 (the dev sign-in scheme the fixtures use), 0058 (the Rust API that is instrumented) and 0060 (the model’s observability control, which states the gap).

Agreed scope

  • Flows: the 7 user-facing CALM flows, sign-in-flow, view-today-flow, add-event-flow, edit-event-flow, edit-task-flow, toggle-task-flow and overdue-triage-flow. A flow is user-facing when one of its transitions uses the user-uses-web-app relationship; today that is exactly these 7.
  • Checked binding: every test is tagged with its flow’s unique-id. A check fails when a user-facing flow has no test or a tag names a flow the model does not define. Until the last slice lands, uncovered flows sit on an explicit pending list that must end empty. Each flow’s entry in the model links its test.
  • Tool: Playwright Test in a new pnpm workspace package, frontend/apps/e2e, consuming the contract and UI like any other client. Chromium only (ADR-0061).
  • Stack: the suite runs on its own throwaway stack: PostgreSQL, the API, the built web app, otel-stack and the stub OIDC provider on their own ports and project name, never the shared calendar Compose project, volume or port 5432 (ADR-0063).
  • Cadence: nightly and on demand (workflow_dispatch, plus a just recipe locally), not on every pull request. Playwright traces and the HTML report are kept as CI artifacts. The binding check needs no browser and runs with the frontend tests.
  • Sign-in: a stub OIDC provider stands in for Google in the E2E stack, so the real login → callback → session → returnUrl round trip runs (ADR-0064). The other flows sign in with the dev scheme as a fixture. The API accepts the stub only when it runs as Development and the stub is on a loopback address; otherwise it refuses to start.
  • Telemetry: the API and the web app emit OpenTelemetry over OTLP only; where it goes is configuration. Locally and in E2E it goes to an otel-stack container (grafana/otel-lgtm: Tempo, Loki, Prometheus, Grafana); in Azure the API’s telemetry goes to Application Insights (ADR-0062). With no endpoint configured, nothing is exported and the API behaves as today.
  • Per-flow assertions, from otel-stack’s query APIs:
    • one trace per flow: the browser action, the API span or spans and the database span or spans share one trace id (the web app sends traceparent), with the span names expected for the flow’s transitions;
    • correlated logs: Loki holds the API’s logs for the flow, carrying that trace id;
    • request metrics: Prometheus has the HTTP request count and duration series for the routes the flow hit;
    • no personal data: no email, event or task title, location, notes, query-string value, session cookie or token in any span, log or metric label, checked against the values the test itself seeded.
  • Privacy rule for telemetry: attributes come from an allow-list (route template, method, status, durations, database operation and table, error kind, opaque ids), never from request or row content (ADR-0062).
  • Local orchestration: otel-stack and the stub are new backing services, which meets ADR-0016’s trigger. ADR-0063 re-evaluates Aspire against Compose now that the backend is Rust: Compose with opt-in profiles is chosen, otel-stack is available opt-in for everyday development, and ADR-0016 is superseded with its test half restated.
  • #104 (Google sign-in test gaps) is a child of this epic; its API-level tests stay in its own scope and may reuse the stub or the in-process fake.

Not in this story

  • database-migration-flow and publish-docs-flow: operator flows with no web UI; they are out of scope for the browser suite.
  • Firefox and WebKit: Chromium only. Another browser would be its own decision.
  • E2E on every pull request: the suite is nightly and on demand; only the binding check runs per PR.
  • Alerts and budgets: stay with #80. This story owns telemetry wiring, including the Azure route.
  • #120: the .NET S8 PR is closed as superseded by the move to Rust.
  • Visual regression, accessibility audits and load tests: not part of these flow tests.
  • Production dashboards in Grafana: otel-stack is a development and test tool only; Azure uses Application Insights and Log Analytics.

Acceptance criteria

  1. Given the model’s user-facing flows, when the nightly E2E run finishes on main, then each of the 7 flows has a test tagged with its unique-id that passed in Chromium against the throwaway stack. Tested by the seven specs in frontend/apps/e2e/tests/, run by the “E2E flows” workflow (e2e.yml) on main at 6f535beb4: run 43705021443, dispatched on 2026-11-15, passed 8 tests (sign-in has two cases) in 1.7 min, 322 s for the whole job.
  2. Given a user-facing flow with no tagged test, or a test tagged with a flow id the model does not define, when the binding check runs on a pull request, then it fails and names the flow or the tag. Tested by binding.test.ts: “binds every user-facing flow of the architecture model to a tagged test or the pending list” runs against the real model and test list. “fails naming a user-facing flow that has no test and is not pending” and “fails naming a tag the model does not define” cover the failures. It runs on pull requests since #909 (#902).
  3. Given a flow test runs, when it queries otel-stack, then it finds one trace holding the browser span, the API span or spans and the database span or spans with the flow’s expected span names, Loki log records carrying that trace id, and Prometheus request count and duration series for the routes the flow hit. Tested by each flow spec through expectFlow (flow.ts); the assertion’s own rules are in telemetry.test.ts (“the trace assertion”, for example “fails when the API span is not under the browser span (two traces glued by name)”). On the API side, tests/api/telemetry.rs has a_request_with_a_traceparent_joins_its_server_and_database_spans_to_that_trace, a_successful_request_exports_one_log_record_with_its_trace_id_and_only_allow_listed_fields and requests_are_counted_and_timed_by_method_route_template_and_status. Sign-in has no browser span, because its pages are full redirects; its traces start at the API’s root span.
  4. Given a flow test seeded titles, notes and a signed-in email, when it scans the flow’s spans, logs and metric labels, then none of those values, nor the session cookie or a token, appears; and a planted value makes the scan fail. Tested by each flow spec’s scan, and by “the personal-data scanner” in telemetry.test.ts (“fails on a seeded title in a span attribute, without repeating the value”, “fails on a token or a cookie header whoever wrote it”, “refuses streams that reach the limit, where Loki may have cut records off”). At the source: no_span_log_or_metric_carries_personal_data_query_values_or_the_session_cookie in telemetry.rs, and “exports no personal value, query string or URL” in the web app’s telemetry.test.tsx.
  5. Given the shared calendar Compose project, or another checkout’s E2E stack, is running, when an E2E run starts and tears down, then those resources are untouched and the run removes only its own containers and volumes. Checked by hand in #772 (#730): a second run went up, passed just e2e check and went down, alongside another run and the shared project’s container, volume and network, and every calendar* resource was compared before and after. In code, just e2e down refuses any project not named calendar-e2e-*. No automated test covers this.
  6. Given a signed-out deep link to /day/<date>, when the person signs in through the stub as an allow-listed verified email, then they land on /day/<date> signed in; and given an email that is not allow-listed, then they land on /signin?error=access_denied with no session cookie. Tested by sign-in-flow.spec.ts (the allow-listed and not allow-listed cases), and at API level by google_sign_in.rs (#104, #750).
  7. Given the API’s Google endpoint or issuer overrides are set, when the API starts as anything but Development, or the override names a non-loopback host, then it refuses to start. Tested by an_override_outside_development_stops_the_api and a_non_loopback_override_stops_the_api_even_in_development in google_overrides_startup.rs, which run the calendar-api binary.
  8. Given no OTLP endpoint is configured, when the API and the web app run, then no exporter is loaded and behaviour and existing tests are unchanged. Tested by nothing_is_exported_without_an_endpoint and without_telemetry_spans_are_disabled_and_only_events_reach_stdout (unit tests in calendar-api/src/telemetry.rs), and by “web telemetry when not configured” › “runs the action directly and registers no tracer provider” in telemetry.test.tsx. The rest of each suite ran unchanged.
  9. Given a deployed staging revision, when a flow runs, then its API trace and logs appear in Application Insights without personal data (owner-verified). Not verified. The route is wired (#769), but the maintainer deferred the owner check on 2026-11-15; it is #927.
  10. Given a failed nightly run, when the maintainer opens it, then the Playwright HTML report, the trace and the failing telemetry assertion are available as artifacts, and the failure is visible without opening the Actions tab. Proved by runs on #876: 43529239198 uploaded the report, trace.zip, the screenshot and the stack logs for a deliberately wrong span name, and 43583755717 opened the failure issue (#898, closed as the proof). Other decisions (not ADR-worthy)

  • User-facing is derived: a flow is user-facing when a transition uses user-uses-web-app, so a new flow in the model needs a test without anyone updating a list.

API

No endpoint changes expected. New settings: the OpenTelemetry OTEL_* variables, and the Development-only Google endpoint and issuer overrides of ADR-0064.

API telemetry (#731) lives in calendar-api/src/telemetry/:

  • Switch: telemetry is on only when OTEL_EXPORTER_OTLP_ENDPOINT or a per-signal endpoint is set. OTEL_EXPORTER_OTLP_PROTOCOL chooses grpc or http/protobuf, which is the default. OTEL_SDK_DISABLED=true and OTEL_<SIGNAL>_EXPORTER=none turn signals off. With no endpoint, no exporter is built, and request spans are disabled at their callsites. Standard output keeps its plain-text format, which shows events only.
  • Server spans: a Router::layer middleware makes one server span per routed request, named <METHOD> <route template>. It is the child of the W3C traceparent the request carries. The layer also records the http.server.request.duration histogram by method, route template and status. Its count is the request count.
  • Database spans: a Diesel Instrumentation is set on each pooled connection in AppState::db(). It makes one client span per query, named <operation> <table>. The span holds db.query.text cut before Diesel’s -- binds:, so bind values are never formatted.
  • Logs: an in-repo bridge layer (logs.rs) exports INFO and above with the trace and span ids of the entered span. It copies only allow-listed fields. opentelemetry-appender-tracing was not used because it copies every field, and an SDK log record cannot drop an attribute afterwards.
  • Request log: the server-span middleware emits one INFO event, request finished, inside each traced request’s span, with only the method, route template and status. It is the record that carries a successful flow’s trace id into Loki; without it, only failures were logged (found while designing #733). It goes to OTLP only: its target (telemetry::http::request_log) is left out of standard output, so the console gets no line per request. Health probes are not logged, and with telemetry off nothing changes.
  • Allow-list: the allow-list is in allow_list.rs. A span processor drops every other attribute and all span events before export.

User guide

This story changes nothing a calendar user sees. For the maintainer:

Run the end-to-end tests

Run the E2E recipe from the repository root. It starts a private stack (database, API, web app, telemetry and a stand-in for Google sign-in), runs every flow in Chromium, and removes the stack afterwards. Your own development database is not touched. A failed run leaves the HTML report and the Playwright trace for the failing test.

Look at a flow’s telemetry locally

Start the optional telemetry service with the development stack, use the app, then open Grafana on its local port to see the trace of each click, the API logs linked to it and the request metrics.

Nightly runs

The suite runs every night on main and can be started by hand from the Actions tab (“E2E flows”, “Run workflow”). When a night’s run fails, an issue titled “E2E flows: the nightly run failed on main” is opened, or commented on if it is already open, with a link to the run. On the run’s page, download e2e-report and open its index.html to see which flow failed and why, e2e-test-results for the trace and screenshot of the failing test, and e2e-stack-logs for the API’s and web app’s logs. Close the issue once the flows pass again.
